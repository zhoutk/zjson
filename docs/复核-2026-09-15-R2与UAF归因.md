### 1.2 根因确认

```cpp
const double nsNew = timeIt(rounds, [&] {           // timeIt = 预热 2 次 + 正式 rounds 次
    for (int i = 0; i < N; ++i) nodes[i] = new Json(1.0);   // 覆盖指针 ⇒ 上一轮节点全部泄漏
});
const double nsDel = timeIt(rounds, [&] {
    for (int i = 0; i < N; ++i) delete nodes[i];     // 同一批指针被 delete 52 次
```

这是我写的，不是你的推测——你的归因**逐字成立**。同一块内存被 `delete` 52 次 ⇒ 池空闲链表把同一地址压入 52 次 ⇒ 后续 `allocate()` 把同一地址交给两个存活节点 ⇒ 一个节点的 `~Json` 在另一个节点正在使用的内存上继续析构 ⇒ 在垃圾位上读到 `usingRef=true` 与**已释放**的 arena 控制块指针 ⇒ `~StoredString` 对已释放控制块做原子减 ⇒ 栈与区域大小（88B）与你我看到的完全一致。

### 1.3 我错在哪（写下来避免重犯）

1. **我做了"换 HEAD 是否复现"的对照，却没做决定性的负对照**——"把可疑负载删掉，看还复不复现"。前者只能证明"跨版本一致"，后者才能证明"是这个负载造成的"。这是典型的混淆实验：探针缺陷与被测代码无关，自然在两份头文件上都复现，于是被我读成了"既有缺陷"。
2. **异常读数被我放过去了**：`new only : 43.10 ns/节点`（而配对测量只有 10.95 ns）本身就是"每轮泄漏 2 万个节点"的信号，我当时注为"测量伪影"就跳过了。**异常值必须先解释掉，再继续推理**——它其实是指向真相的唯一线索。
3. 教训概括：**压测程序自身的生命周期 bug 会以"库缺陷"的面目出现；对任何 sanitizer 报告，先证明复现器无辜。**

我的对照是**同一二进制在两侧各跑 6 组**，比值 0.990–1.017，说明该数据集在本机是**可分辨**的：`c9b4ab7` 稳定在 ~152 MB/s、`HEAD` 稳定在 ~138 MB/s。你观察到的"重编译后 200↔138 翻转"更可能是**编译产物差异**（该数据集单次解析仅约 25 µs，对代码布局/对齐极敏感），而不是"无法区分代码差异"。就本轮而言，flat_10KB 的 0.907× 与 flat_100KB 的 0.923× 同向、且对照组同时刻为 0.99–1.01，因此我判断这个回退是**真实**的。建议对外引用该数据集前做"同源码重编译对拍 + 对照组"两步确认。

### 3.3 机制定位与**已验证的修复**

回退随"每节点字符串数"单调变化（flat 最重、mixed_1MB 几乎为零），指向**每个被存储字符串的固定开销**。读代码后定位到 move 构造/赋值末尾的这段：

```cpp
if (other.usingRef) {
    other.usingRef = false;
    new (static_cast<void*>(&other.payload)) string();   // 把 moved-from 对象改回"自有空串"
}
```

解析热路径是 `val->valueString = std::move(s)`：`s` 处于借用态、目标默认构造（自有空串）⇒ 走"析构 owned + placement-new ViewPayload"分支，紧接着这段又**析构(空) + placement-new string + 随即析构**——纯开销，每个被存储字符串一次。

**变异实验**：只用一行把 moved-from 留在"空借用态"（arena 已被 move 走，只需把 `ref` 置空），其余不变：

```diff

                     if (usingRef) {
                             new (static_cast<void*>(&payload)) ViewPayload(std::move(other.payload.view));
-                            other.usingRef = false;
-                            new (static_cast<void*>(&other.payload)) string();
+                            // 留在（已经为空的）借用态即可：ViewPayload 仍然存活、析构函数
+                            // 本来就正确，只需丢弃残留的 ref。
+                            other.payload.view.ref = string_view();
                     } else {
```

```diff
                     if (other.usingRef) {
-                            other.usingRef = false;
-                            new (static_cast<void*>(&other.payload)) string();
+                            other.payload.view.ref = string_view();
                     }
```

并同步把不变量写成显式判断（moved-from 节点会是 `usingRef == true` 且 arena 为空）：

```diff
-            bool borrowed() const noexcept { return usingRef; }
+            bool borrowed() const noexcept { return usingRef && payload.view.arena != nullptr; }
```

**实测结果（6 组交替 + 对照组）**：parse 顺序修正后 **0.952× → 0.990×**，即回收了约 3.8 个百分点；机制确认。

## 四、`compactReserveHint()`：两个问题

### 4.1 注释的论据不成立（对正确性无害）

注释写"紧凑输出不可能超过源长（每个重转义字符串 ≤ 源跨度、空白被丢弃）"。字符串部分成立，**数字部分不成立**——指数写法的整数字面量在最短往返输出下会变长：

| 源文本 | 源长 | 紧凑输出长 |
| --- | ---: | ---: |
| `[1e5,1e5,1e5,1e5,1e5,1e5]` | 25 | **43** |
| `[1e15,1e15,1e15,1e15]` | 21 | **69**（3.3×） |

`reserve` 只是提示，**不会导致输出错误**；但结论是：对数字密集的文档，`+64` 的余量不足，提示会**欠预留**，从而产生额外扩容——恰好削弱了它本要解决的问题。建议把注释改成"字符串不会变长、数字增量有界但未计入"，或按数字个数累计余量。

### 4.2 可达的内存放大（建议处理）

提示取自"前 16 个兄弟中任一借用串所属 arena 的**整份源文本长度**"。于是：从一份大文档里借出一个短串、 graft 到新容器，`toString()` 就会按**整份源文档**预留。

实测：源文档 1,000,024 B → 输出 12 B → 预留 1,000,088 B，**约 8.3 万倍放大**（输出正确）。

这是"解析大配置 → 组装小摘要"这种常见写法的真实代价：短命但可达 MB 级。可选处置：

* **保守**：命中借用提示时，若 arena 源长明显大于一个便宜的规模下界，则回退 `estimateSerializedSize`；
* **折中**：把提示**钳制**在某个上限（例如 4 MB），或按根部直接子节点个数缩放；
* **保持现状但写进文档**，明确"该提示对 graft 场景会过度预留"。

我倾向"钳制 + 文档说明"，因为它保留 O(1) 的快速路径，且过预留只是内存峰值、不改变语义。

## 五、其他（无实测缺陷，属稳健性建议）

1. **move 构造/赋值用 placement-new 覆盖 moved-from 的 `ViewPayload` 前没有先析构它。** 今天是良性的（`shared_ptr` 被 move 后保证为空，其析构是 no-op），但该不变量是隐式的；§3.3 的补丁顺带消除了这个隐患。
2. **`borrowedArena()` 不检查 `usingRef`**，非借用态下读的是联合的非活跃成员（UB）。当前所有调用点都由 `borrowed()` 守卫，所以安全；但接口形状是"陷阱型"，且若采纳 §3.3 补丁则**必须**同步收窄 `borrowed()`（补丁已含），否则 moved-from 节点会出现"`borrowed()` 为真、arena 为空"的组合。
3. `makeOwned()` 只被 3 个赋值运算符调用且调用后立即覆写，**不存在内容丢失**——已确认。
4. §6 各项我已核对落地：`static_assert(sizeof(Json) == 128)` 在 `test_number.cpp`；`parseWithArena` 抽取正确；新增的 `parse_destroy_churn_with_surviving_documents_is_clean` 覆盖了"存活文档跨轮持 arena + clone/take/add/extend/mergePatch/concat + 中途替换存活者"，正对上一轮的假阳性类别，设计合理。
