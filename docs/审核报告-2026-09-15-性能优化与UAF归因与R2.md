## 二、"既有 StringArena UAF"（该文档 §5）：**不存在——是复现器自身的缺陷**

这是本轮最重要的结论。报告中的 ASan 栈被**完整复现**，但根因在探针，不在库：

### 复现链

`plan_probe3c.cpp` 的 **H 节（"pure node create+destroy"）**：

```cpp
const double nsNew = timeIt(rounds, [&] {          // timeIt 内部先 fn(); fn() 预热再循环 50 次
    for (int i = 0; i < N; ++i) nodes[i] = new Json(1.0);   // 只 new，覆盖指针 ⇒ 泄漏上一轮节点
});
const double nsDel = timeIt(rounds, [&] {
    for (int i = 0; i < N; ++i) delete nodes[i];   // 对同一批指针 delete 52 遍 ⇒ 同一节点被多次 delete
});
```

两次 `timeIt` 各含预热 2 次 + 正式 50 次 = 每个节点最终被 `delete` 约 52 次。**同一节点被析构两遍**时，第二遍 `~Json` 在已归还池的内存上读到残留位：

* `releaseChildren()` → `deleteJson(残留 child 指针)` → 在垃圾内存上继续析构；
* 垃圾位里恰好有 `usingRef=true` + 指向**已释放** `make_shared<StringArena>` 控制块的指针 → `~StoredString` 对其引用计数做减法 → **heap-use-after-free WRITE of size 4**，栈为 `~StoredString ← ~Json ← deleteJson`，区域大小 88 字节（libc++ 控制块 16B + StringArena 72B）——与文档 §5 的报告**逐帧一致**。

第一次错误 `delete` 还把同一块内存**两次压入池空闲链表**，于是 H 节之后的任何解析都可能拿到同一地址两次，在 I 节引爆（报告的现象正是"多数据集 × 多次迭代 + 存活文档 + 节点 churn 的组合才复现"——因为这个组合必然包含 H 节或等价物）。

### 证据

1. **原始探针 + 当前头文件 + ASan**：报告完全相同的栈（本机复现，栈帧逐条对照一致）。
2. **插桩双删检测器**（在 `~Json` 中对已释放形状打标）：在 H 节当场报 `DOUBLE-DELETE`。
3. **修复探针后同一负载全绿**：把 H 节改成"删除与分配在同一循环内配对"（`delete nodes[i]; nodes[i] = new Json(1.0);`，增量部分并入 nsNew）后，同一份"多数据集 × 多次迭代 + 存活文档 + churn"在 ASan 下 **0 报告、退出码 0**——新头文件、旧头文件（`git show HEAD`）双双通过。
4. 其余负载（官方 bench 全节、probe5/probe6、ctest 14/14）在 ASan 下均无报告。

### 结论

* 库本身**没有**这个 UAF；文档 §5 应撤回，P0 项闭环方式为"复现器修正 + 回归测试"，而非库修改。
* `docs/性能优化实施与评估-2026-09-15.md` §5 与 §6 P0 的表述需要更正（本轮已在 §6 表格标注）。
* 教训（与前几轮"探针错了 4 处"同类）：**压测程序自身的指针/生命周期 bug 会以"库缺陷"的面目出现**；对任何 ASan 栈，先证明复现器无辜（把可疑负载删掉看是否复现），再怀疑库。

## 四、R2：StoredString 64B → 40B，节点 176B → 128B

### 设计

`StoredString` 的两态（自有 `std::string` / 借用 arena 视图）**从不同时存活**——每个修改点都切换标记并丢弃另一态。因此改为**标记联合**：

```cpp
struct ViewPayload { string_view ref; std::shared_ptr<StringArena> arena; };  // 32B
union Payload { string owned; /*24B*/ ViewPayload view; /*32B*/ };            // 32B
Payload payload; bool usingRef;                                               // 40B
```

* 所有权语义不变：复制/移动/赋值按标记搬运活跃侧；`strRef()` 先把 arena 挪到局部变量再物化（借用字节可能就在 arena 里）；`makeOwned()` 在写自有侧前先析构视图侧。
* `fromView` 走标签构造函数返回纯右值，整条链（`fromView → parse_stored_string → 调用方`）由 C++17 保证的复制消除零移动、零析构往返。
* 生命周期审计不变：视图的 `ref` 只指向 arena（`source` 或 chunk），arena 由 `shared_ptr` 持有；新实现没有任何裸视图逃逸路径。
* 节点收益：`sizeof(StoredString)` 64→40，两处成员（`name`/`valueString`）各省 24B，**`sizeof(Json)` 176→128**（static_assert 已锁），池块随之 128B，缓存与带宽同步受益。

### 实测（5 数据集 × 12 轮轮转 A/B，HEAD vs 本工作区，中位数）

| op | 几何平均 | 亮点 |
| --- | --- | --- |
| copy | **+16.1%**（mixed_1MB +41%） | 节点变小直接受益，符合预期 |
| stringify | +1.4~4.9%（各轮 5 数据集组合） | reserve 提示 + 节点变小 |
| parse | flat_100KB **+9%**，mixed 持平；flat_10KB 不可判读 | 见下"测量备注" |

**测量备注（诚实记录）**：flat_10KB（300 键宽对象，单次解析仅 ~20µs）的跨进程读数对**构建产物本身**敏感：同一份源码重编译后读数即从 ~200 MB/s 翻到 ~138 MB/s（旧头文件 + 一次性插入的哑函数验证过；新旧混合构建亦落在同一簇）。即该数据集区分不了代码差异，只能用于粗粒度趋势。可信信号来自 flat_100KB 及更大的数据集：parse +9%、copy +9~41%、stringify +1~4%。对外引用 flat_10KB 前请先提高迭代数并做多次重编译对拍。

### R2 未及项（记录）

* "每串 `shared_ptr` 的 14% 开销"没有消除：借用串仍各自持 `shared_ptr<StringArena>`。消除它需要"arena 由根节点独占持有 + 子节点裸指针"的所有权重设计，而 `take()`/`clone()` 的子树脱离语义会让裸指针悬垂——需要先定义"脱离即物化"的规则，属独立立项，本轮不做。
* `R4-1 detach()`、R5-2 SAX、CI/LSAN/TSAN 矩阵：维持待办。
