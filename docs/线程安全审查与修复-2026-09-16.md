# 线程安全审查与修复 — 2026-09-16

> 审查范围：`src/zjson.hpp`（4686 行）、`CMakeLists.txt`、`bench/bench_main.cpp`、`tests/*`。
> 结论先行：**本库此前不是线程安全库 —— 连「并发只读同一棵树」都不安全**。本次已修复，接口签名零改动，实测性能无损失（多数指标反而更好）。

---

## 1. 结论

| 并发场景 | 修复前 | 修复后 |
|---|---|---|
| 不同文档分别在不同线程使用（parse/toString/增删） | ✅ 安全（可扩展 ×2.8~3.1） | ✅ 安全（×2.86） |
| 节点跨线程分配/释放（含分配线程已退出） | ✅ 安全（每线程池 + 永不释放） | ✅ 不变 |
| **同一棵树、多线程只读（const）** | ❌ **数据竞争，实锤堆破坏** | ✅ **安全**（纯读） |
| 同一棵树、多线程读写 | ❌ 不安全 | ❌ 仍不安全（与 `std::string` 同，见 §6） |

## 2. 两个实锤的数据竞争（修复前）

两处都发生在 **`const` 读路径**上，所以「把文档当 const 共享」这种最保守的用法也是错的。

### 竞争 A：`Json::keymap` 懒构建（`buildKeymap()`）

`operator[]` / `contains` / `findPtr` / `at()` / `atRef()` 都会走到 `directMemberPtr()`，它对**尚未建索引**的对象执行：

```cpp
if (!this->keymap) buildKeymap();          // const 方法里写 mutable 成员
return this->keymap->find(key);
```

`buildKeymap()` 先 `delete keymap` 再 `keymap = new ...` 再逐项 `assign()`。两个线程同时首次查询：

- 双方都读到 `keymap == nullptr` → 都进入 `buildKeymap()`
- 线程 B 执行 `delete keymap` 时，线程 A 正在往同一张表里 `insertNew()`/`grow()`
- → **use-after-free 写 + heap-buffer-overflow 读**

**ASan 实证**（`mode=0 rounds=60 threads=8 keys=4000`）：

```
==8092==ERROR: AddressSanitizer: heap-buffer-overflow ... READ of size 8 at ... thread T3
    #0 JsonKeyIndex<Json>::insertNew(...)            zjson.hpp:427
    #1 JsonKeyIndex<Json>::grow()                    zjson.hpp:465
    #3 Json::buildKeymap() const                     zjson.hpp:3719
    #4 Json::contains(...) const                     zjson.hpp:2458
freed by thread T8 here:
    #4 JsonKeyIndex<Json>::allocate(...)             zjson.hpp:438   ← 另一线程 delete 了正在填的表
```

### 竞争 B：`StoredString::strRef()` 原地物化借用键名

`JsonEntry::key()` / `JsonConstEntry::key()` 返回 `const string&`，而解析出的成员键名是从 arena **借用**的视图，于是 `key()` 不得不就地改写节点的 `mutable Payload`：析构 `payload.view`（内含 `shared_ptr`）→ placement-new 一个 `std::string` → 翻转 `usingRef`。

两个线程同时对同一节点调用 `key()`：对同一个 32 字节 union 并发析构/构造 → `string_view` 被撕碎、`shared_ptr` 控制块被双重递减（arena 提前释放）。

**ASan 实证**（`mode=1 rounds=40 threads=8`，文档刻意只含 1 个借用键名，使 arena 引用计数恰为 1）：

```
==14104==ERROR: AddressSanitizer: out of memory: allocator is trying to allocate 0x305f796570 bytes
    #8 ZJSON::detail::StoredString::strRef() const    zjson.hpp:312   ← 读到被撕碎的 view，size 是垃圾值
    #9 ZJSON::JsonConstEntry::key() const             zjson.hpp:4427
```

（分配 0x305f796570 字节 = `ref.size()` 读到了半个指针，即被并发改写的现场证据。）

### 次要发现（非竞争，但与线程契约相关）

- `errorSentinel()` / `jsonNodeAllocator()`：`thread_local` + 进程生命期，**正确**。跨线程释放安全的前提（slab 永不释放）成立。
- `StringArena` 以 `shared_ptr` 随节点共享：引用计数是原子的，并发只读下安全 —— 但正是「每节点一次原子递增/递减」成了下面的性能优化点。
- 池的 `~SlabAllocator` 隐式析构只会释放 `slabs` 这个 vector 的堆数组，不会释放 slab 本体 → 与注释「永不释放」一致，无问题。

## 3. 修复方案（对外接口零改动）

### 修复 A：key 索引改为「构建后原子 CAS 发布」

`keymap` 由裸指针改为 `std::atomic<JsonKeyIndex<Json>*>`（同样 8 字节，`sizeof(Json)` 仍为 128，`test_number.cpp` 的布局 `static_assert` 不变）：

```cpp
detail::JsonKeyIndex<Json>* publishKeymap() const {
    std::unique_ptr<JsonKeyIndex> fresh(new JsonKeyIndex());
    fresh->reserve(childCount());
    for (Json* cur = this->child; cur; cur = cur->brother)
        fresh->assign(cur->name.view(), cur);
    JsonKeyIndex* expected = nullptr;
    if (keymap.compare_exchange_strong(expected, fresh.get(), acq_rel, acquire))
        return fresh.release();   // 我赢了
    return expected;              // 别人赢了，直接用他的（描述的是同一条链）
}

const Json* directMemberPtr(string_view key) const {
    if (type != Object || !child) return nullptr;
    JsonKeyIndex* index = keymap.load(std::memory_order_acquire);
    if (!index) index = publishKeymap();
    return index->find(key);
}
```

要点：**失败者不需要重试**（赢家建的是同一棵链的索引），因此竞争是「零成本收敛」；读者永远不会释放别人正在用的表。所有写入侧的失效统一走 `invalidateKeymap()`（并发读写仍受契约禁止，见 §6）。

### 修复 B：成员键名在解析期即为 owned

新增 `JsonParser::parse_stored_key()`（与 `parse_stored_string()` 同一套扫描逻辑），对象键名直接落成 `std::string`，不再借用 arena 视图。于是 `key()` 永远命中 `strRef()` 的 owned 分支 —— **彻底不存在那个写操作**。

字符串**值**仍然借用 arena：真正省内存/省拷贝的是值，不是键名；而且值没有任何 const 读路径会去物化它（`str()`/`view()` 都是纯读）。

附带一个可以写进测试的强契约：`key()` **不分配、因此不可能抛异常**（见 §5）。

### 一处必须绕开的性能坑

第一版 `invalidateKeymap()` 写成了 `delete keymap.exchange(nullptr)`。`exchange` 在 x86 上是 `lock xchg`（≈20 周期），而它在**每个节点析构**时都会跑（`deleteJson` 和 `~Json` 各一次）——实测节点 churn 从 19.62 ns 涨到 33 ns，parse 掉 10%+。改成与原实现等价的「load + 判空 + store」后恢复：

```cpp
void invalidateKeymap() noexcept {
    JsonKeyIndex* index = keymap.load(std::memory_order_relaxed);
    if (index) { keymap.store(nullptr, relaxed); delete index; }
}
```

（安全性等价：并发的「写 vs 读」本来就在契约之外，`exchange` 并不会更安全，只是更慢。）

## 4. 性能 A/B（同机、clang 22.1.8 -O2、各 3 次取中位数）

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 节点 churn（create+destroy） | 19.62 ns | 20.79 ns | +6%（噪声级） |
| parse+stringify 单线程 | 102.8 MB/s | 103.0 MB/s | **+0.2%** |
| parse+stringify 4 线程 | 291.8 MB/s | 293.1 MB/s | **+0.5%** |
| 4 线程扩展比 | ×2.84 | ×2.86 | — |
| `operator[]` 链式读（200 层） | 21822 ns | 22305 ns | +2.2% |
| `atRef()` 读 | 23.1 ns | 25.0 ns | +8%（= 一次 acquire load） |
| `findPtr()` 写 | 14.9 ns | 16.1 ns | +8% |
| copy flat_10KB | 766.7 MB/s | 1410.5 MB/s | **+84%** |
| copy flat_100KB | 839.9 MB/s | 1427.2 MB/s | **+70%** |
| copy mixed_10KB/100KB/1MB | 500/512/421 MB/s | 722/674/579 MB/s | **+32~44%** |
| parse（5 个数据集） | — | — | **-0.2% ~ +7.4%** |
| stringify（5 个数据集） | — | — | **-3% ~ +1.9%** |

**为什么 copy 大涨**：修复 B 让键名不再携带 `shared_ptr<StringArena>`，深拷贝一棵树时每个节点省掉一次原子递增/递减 —— 拷贝本来就是每节点一次的路径，收益直接兑现。

**唯一的固定开销**：`directMemberPtr` 命中路径上多了一次 acquire load（x86-64 上就是一条普通 MOV），体现为 `atRef`/`findPtr` +1~2 ns。这正是「不改变接口、性能损失不能太多」约束下能买到的最便宜的线程安全。

## 5. 测试

**新增 `tests/test_thread_safety.cpp`（4 个用例）**，已接入 CMake（链接 `Threads::Threads`）：

1. `concurrent_const_reads_of_one_shared_document_are_safe` —— 8 线程 × 30 轮，每轮共享一份**新解析**的文档（2000 键宽对象 + 转义键/值 + 数组），跑完整个 const 读电池：`contains`/`operator[]`/`findPtr`/`at`/`atRef`/迭代含 `key()`/`toString`/深拷贝/`==`。每轮新文档是为了让「首次建索引」这个竞争窗口每轮都被并发踩到。
2. `concurrent_key_materialization_never_rewrites_the_node` —— 竞争 B 的最小复现：文档只含 1 个借用键名（arena 引用计数 = 1），8 线程 × 400 轮同时 `key()`。
3. `nodes_may_be_allocated_and_released_on_different_threads` —— 生产者线程建完文档退出，消费者线程增删读，最后在主线程释放。
4. `independent_documents_are_usable_in_parallel` —— 4 线程各自 parse/改/删/序列化。

验证方式（Windows 无 TSan，clang64 提供 ASan）：

- **修复前**：用 `tools/` 里的复现器（§2 的两个 mode）→ ASan 分别报 heap-buffer-overflow（竞争 A）与 OOM/撕碎的 size（竞争 B）。
- **修复后**：`test_thread_safety` 普通 `-O2` 与 `-fsanitize=address` 均 4/4 通过，ASan 无任何报告。

**改写 `tests/test_exception_safety.cpp`**：原 3 个用例专门验证「`strRef()` 物化借用键名失败后文档仍一致」—— 该路径已被修复 B **有意删除**。改写为更强的契约：用全局 `operator new` 故障注入布防「第 1 次分配即失败」，然后证明 `key()` **一次分配都不发生**（布防的计数器原样保留），从而既不可能抛异常也不可能竞争；并保留「布防时下一个真实分配确实抛 `bad_alloc`」来自证注入器仍然有效。

**回归**：14 个既有套件全部通过（api_coverage 53、advanced 18、spec 25、parse_coverage 19、jsontestsuite 20、number 13、rfc_cases 5、conformance 2、json_checker 2、object/array/parse/more 各 1）。

## 6. 仍然不安全的部分（必须写进文档，无法在不改接口的前提下修复）

1. **同一棵树的并发读写**：`add/remove/operator=`/`appendNodeToJson` 等会改链表、改 `lastChild`、失效并重建索引。加锁意味着每节点一个 mutex（节点 128B → 168B+，且 `operator[]` 返回值语义会被锁打散），或引入读写锁（`shared_mutex` 会让 `atRef` 从 25 ns 涨到数百 ns）。这与 `std::string`/`nlohmann::json` 的定位一致：**容器不是线程安全对象**。需要并发读写时请用副本或外部同步。
2. **跨模块卸载**：header 内联进每个模块，跨 DLL 传递并在模块卸载后析构的文档不安全（池是模块内 `thread_local`）。
3. **池驻留按线程峰值不回收**：实测 64 个短命线程 × 4 万节点 → 进程永久增长 ≈440MB。请复用线程。

README（中英）第 2 条契约已同步更新为「并发只读安全 / 并发读写仍不安全」。

## 7. 后续可选优化（非本次范围，按收益排序）

1. **`StringArena` 引用计数改为 `shared_ptr` 之外的 intrusive 原子计数**：可让 `StoredString` 的借用分支从 32B 缩到 24B，为节点瘦身（128 → 120 或增加一个缓存字段）腾出空间。
2. **宽对象首次查找的 O(n) `childCount()`**：`publishKeymap()` 先 `childCount()` 再遍历一次，共两趟；可在解析期把 Frame 里的索引直接转移给容器（零成本），并把 ≤16 键的对象改为纯线性扫描（省掉索引分配）。这对「并发只读」尤其有价值 —— 宽对象**一次都没被并发建过索引**。
3. **`removeDirectChildrenByKey`/`unlinkChild` 现在每次都 `delete` 索引**：Patch/批量删除场景下索引会被反复重建，可改为标记脏位 + 下次读取时重建。
4. **pretty 打印的 `appendIndent` 每次 `string(n,' ')`**：每行一次堆分配，可换成复用缓冲。
5. **`parse_string` 的 `\u` 逃生**：每个 `\uXXXX` 都 `substr` 出一个临时 `std::string`，可改为栈上 4 字节手动解析（消除热路径分配）。
