## 2. 实施的改动（全部在 `src/zjson.hpp`）

新增**一个**数据结构，替换**两处**哈希表：

```cpp
template <typename Node>
struct JsonKeyIndex {          // detail 命名空间，约 100 行
    struct Slot { size_t hash; Node* node; };
    std::unique_ptr<Slot[]> slots;
    size_t capacity, count;
};
```

* 平坦数组 + 2 的幂容量 + 线性探测，负载因子 ≤ 1/2（保证探测必然终止）；
* **槽位只存 hash 和节点指针，键文本每次比较时从 `node->name` 读回**——因此不存在任何会悬垂的 `string_view`，也不复制任何键；
* `assign` 语义等价于 `unordered_map::operator[]`（重复键后者胜出）。

**接入两处：**

1. **解析器 `Frame`**（原来 `std::unordered_map<string_view, Json*>`，>16 键才启用）。
   保留 ≤16 键的内联线性小索引——实测它只占 2.5%，且完全免分配。
   同时 `Frame` 里 `unordered_map`（≈56B）换成 `JsonKeyIndex`（24B），**Frame 每层缩小约 32B**。
2. **惰性 `keymap`**（原来 `std::unordered_map<string, Json*>`）。
   每个键原来要复制一个 `std::string` + 分配一个哈希节点；现在零复制、零逐键分配。

> 生命周期审计（报告中标记的主要风险）：旧实现把 `string_view` 作键，改名即悬垂；新实现**从不存键视图**，比较经由节点自身的 `name`，所以改名只会让旧条目查不到（与旧实现同样查不到新名），不会读到已释放内存。结构性改动处的"整表作废"纪律（`unlinkChild` / `removeDirectChildrenByKey` / `appendNodeToJson`）原样保留。

## 5. 第二轮（R2）：StoredString 标记联合 + stringify reserve

### 5.1 设计

`StoredString` 的两态（自有 `std::string` / 借用 arena 视图）从不同时存活，故改为**标记联合**（`union { string owned; struct { string_view ref; shared_ptr<StringArena> arena; } view; }` + 1 字节标记），成员手动管理。附带一个 `borrowed()` / `borrowedArena()` 访问器供 `toString()` 复用。

`compactReserveHint()`：解析出的文档可从**任一**借用字符串反查到 arena，用**源文本长度 + 64** 作为紧凑输出的 reserve 上界，省掉 `estimateSerializedSize` 的全树预遍历；查不到（前 16 个兄弟内无借用串）或 pretty 路径仍走预遍历。

### 5.2 收益（`c9b4ab7` → `HEAD`，6 组交替 + 同二进制对照）

| 指标 | 结果 | 对照组 |
| --- | --- | --- |
| copy 几何平均 | **+16.6%**（mixed_1MB **1.46×**） | 0.991× |
| stringify 几何平均 | +1.7% | 1.001× |
| 节点 create+destroy | **22.65 → 19.78 ns**（−12.7%） | — |
| 4 线程 parse+stringify 扩展比 | ×2.67 → **×3.10** | — |
| `sizeof(StoredString)` / `sizeof(Json)` | 64 → **40** / 176 → **128** | — |

copy 与池开销的改善与"节点变小"直接对应，方向明确。**stringify 只有 +1.7%**，与第五轮报告记录的 +4.9% 不符。

### 5.3 但 parse 回退约 4.8%（机制已定位，补丁已验证）

同一组 A/B 中 parse 的几何平均为 **0.956×**（对照组修正后 **0.952×**）：

| 数据集 | old MB/s | new MB/s | 比值 | 对照组比值 |
| --- | ---: | ---: | ---: | ---: |
| flat_10KB | 152.09 | 138.01 | **0.907×** | 0.990× |
| flat_100KB | 194.13 | 179.11 | **0.923×** | 1.009× |
| mixed_10KB | 175.79 | 171.89 | 0.978× | 1.002× |
| mixed_100KB | 186.18 | 182.02 | 0.978× | 1.002× |
| mixed_1MB | 184.06 | 183.53 | 0.997× | 1.017× |

对照组（同一二进制两侧各 6 组）几何平均 1.004×，**不是运行顺序噪声**；回退幅度随"每节点字符串数"单调递减，指向每个被存储字符串的固定开销。

**机制**：move 构造/赋值末尾会把 moved-from 对象"改回自有空串"：

```cpp
if (other.usingRef) {
    other.usingRef = false;
    new (static_cast<void*>(&other.payload)) string();   // 析构(空) + placement-new + 随即析构
}
```

解析热路径 `val->valueString = std::move(s)` 每次都会撞上这段，**纯开销**。

**验证过的修复（3 行）**：把 moved-from 留在（已经为空的）借用态，并同步收窄 `borrowed()`：

```diff
-                            other.usingRef = false;
-                            new (static_cast<void*>(&other.payload)) string();
+                            other.payload.view.ref = string_view();     // arena 已被 move 走
-            bool borrowed() const noexcept { return usingRef; }
+            bool borrowed() const noexcept { return usingRef && payload.view.arena != nullptr; }
```

**实测**：parse 顺序修正后 **0.952× → 0.990×**（回收约 3.8 个百分点）；`build` exit 0、`ctest` **14/14**、**ASan 全量 ctest 14/14 零报告**。
补丁未落地（保持工作区与提交一致），文件在 `d:/msys64/tmp/r2fix/zjson.hpp`，完整 diff 与复核细节见 [`docs/复核-2026-09-15-R2与UAF归因.md`](复核-2026-09-15-R2与UAF归因.md) §3.3。

### 5.4 关于 flat_10KB "不可判读"

第五轮报告认为该数据集对构建产物敏感、只能看粗粒度趋势。我的对照（同一二进制两侧各 6 组，比值 0.990–1.017）显示它在本机**可分辨**：`c9b4ab7` 稳定 ~152 MB/s、`HEAD` 稳定 ~138 MB/s。建议对外引用前做"同源码重编译对拍 + 对照组"两步，而不是整体放弃该数据集。

## 6. `compactReserveHint()` 的两个问题

**6.1 注释论据不成立（对正确性无害）**：注释称"紧凑输出不可能超过源长"。字符串部分成立，**数字部分不成立**——指数写法的整数字面量在最短往返输出下会变长：

| 源文本 | 源长 | 紧凑输出长 |
| --- | ---: | ---: |
| `[1e5,1e5,1e5,1e5,1e5,1e5]` | 25 | **43** |
| `[1e15,1e15,1e15,1e15]` | 21 | **69**(3.3×) |

`reserve` 只是提示、不影响输出正确性；但对数字密集文档 `+64` 余量不足 ⇒ **欠预留** ⇒ 额外扩容，削弱了它本要解决的问题。

**6.2 可达的内存放大（建议处理）**：提示取自"前 16 个兄弟中任一借用串所属 arena 的整份源文本长度"。从大文档借出一个短串 graft 到新容器后，`toString()` 会按整份源文档预留——实测 1,000,024 B 源 → 12 B 输出预留 1,000,088 B，**约 8.3 万倍**（输出正确）。短命但可达 MB 级，建议**钳制上界**或在该提示明显大于规模下界时回退预遍历，并写进文档。

## 7. 勘误：本文曾断言存在的"既有 StringArena UAF"**并不存在**

本文早期版本（第一轮）在 §5 记录了一个 ASan `heap-use-after-free`，并判定为"与本次优化无关的既有库缺陷"。**该判定错误，现已撤回。**

* **真实原因**：我在 `plan_probe3c.cpp` 的 H 节把分配与释放放进了**两个独立的 `timeIt` 调用**，而 `timeIt` 会先预热 2 次再跑 `rounds` 次——于是同一批 20000 个指针被 `delete` 了约 52 次，池空闲链表把同一地址压入 52 次，后续 `allocate()` 把同一地址交给两个存活节点，一个节点的析构便作用在另一节点正在使用的内存上。
* **独立复现（唯一变量 = H 节是否重复 delete）**：原探针 → ASan **1 处报告、退出码 1**；改为分配/释放配对后 → **0 报告、退出码 0**，且在 `HEAD` 与 `f8f90eb` 两份头文件上**都**为 0。库侧无此缺陷。
* **我曾"排除"的线索其实指向真相**：`new only : 43.10 ns/节点`（配对测量仅 10.95 ns）正是"每轮泄漏 2 万个节点"的信号，当时被我注为"测量伪影"跳过。
* **教训**：对任何 sanitizer/崩溃报告，先做**负对照**——"把可疑负载删掉，看是否还复现"——再怀疑被测代码；"换一个版本是否复现"只能证明跨版本一致，不能证明因果。
* **代码侧**：库未改动；新增的 `TestAdvanced.parse_destroy_churn_with_surviving_documents_is_clean` 覆盖了这类"存活文档 + churn + clone/take/add/extend/concat"的组合，是合适的回归防线。
