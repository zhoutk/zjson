## 1. 先验证方案，再动手（本次的第一步）

原报告（《审核报告-2026-09-15-R5-1与N项验收》§3.2）给出的方案，先用独立探针逐条实测，**不靠论证靠数字**：

| 方案候选 | 实测 | 判定 |
| --- | --- | --- |
| 解析器 keyIndex 换开放寻址 | 索引占 flat_10KB 解析的 **41.9%**（13.2 µs / 30.8 µs）；`unordered_map<string_view,Json*>` 45 ns/key@300、77 ns/key@3000，开放寻址 8.6 / 29.9 ns/key（**5.28× / 2.57×**） | **采纳** |
| 惰性 keymap 换开放寻址 | 建表+N 次查询：**11.6×@300、10.5×@3000** | **采纳** |
| `memchr` 大步扫字符串 | **0.42×（更慢）**——字符串平均 8 字符，调用开销压过收益 | **否决** |
| 查表跳空白 | bench 数据集**完全不含空白**，收益 ≈0 | **否决** |
| 缩小 Frame 内 384B 小索引 | 2.77 ns/容器，仅 mixed_1MB 的 **1.1%**；且线性扫描只占 2.5% | **否决**（保留内联小索引） |
| 小索引加哈希预筛选 | 3.78 vs 3.14 ns/key，**1.2× 更慢**，Frame 还多 128B | **否决** |
| 每字符串一个 `shared_ptr<StringArena>` | `fromView(shared_ptr 按值)` 8.5 ns/串，借用裸指针 0.54 ns；mixed_1MB 约 10.4 万串 ≈ **14%** | **暂缓**（见 §5） |
| 节点分配（池） | new+delete **10.95 ns/节点**（≈11%），池已足够好 | 保留 |

**关键佐证**：优化前 flat 文档 102–131 ns/节点，mixed 文档仅 47–52 ns/节点；二者差额与独立测得的 `unordered_map` 每键成本（45–77 ns）**几乎完全吻合**——宽对象慢的唯一原因就是它。

> 报告中被实测推翻的三条：`memchr`、空白查表、"+5~10% 扫描优化"。
> 报告中被实测**证实且低估**的一条：解析期键索引。

## 2. 实施的改动（全部在 `src/zjson.hpp`）

新增**一个**数据结构，替换**两处**哈希表：

```cpp
template <typename Node>
struct JsonKeyIndex {          // detail 命名空间，约 100 行
    struct Slot { size_t hash; Node* node; };
    std::unique_ptr<Slot[]> slots;
    size_t capacity, count;
};
```

* 平坦数组 + 2 的幂容量 + 线性探测，负载因子 ≤ 1/2（保证探测必然终止）；
* **槽位只存 hash 和节点指针，键文本每次比较时从 `node->name` 读回**——因此不存在任何会悬垂的 `string_view`，也不复制任何键；
* `assign` 语义等价于 `unordered_map::operator[]`（重复键后者胜出）。

**接入两处：**

1. **解析器 `Frame`**（原来 `std::unordered_map<string_view, Json*>`，>16 键才启用）。
   保留 ≤16 键的内联线性小索引——实测它只占 2.5%，且完全免分配。
   同时 `Frame` 里 `unordered_map`（≈56B）换成 `JsonKeyIndex`（24B），**Frame 每层缩小约 32B**。
2. **惰性 `keymap`**（原来 `std::unordered_map<string, Json*>`）。
   每个键原来要复制一个 `std::string` + 分配一个哈希节点；现在零复制、零逐键分配。

> 生命周期审计（报告中标记的主要风险）：旧实现把 `string_view` 作键，改名即悬垂；新实现**从不存键视图**，比较经由节点自身的 `name`，所以改名只会让旧条目查不到（与旧实现同样查不到新名），不会读到已释放内存。结构性改动处的"整表作废"纪律（`unlinkChild` / `removeDirectChildrenByKey` / `appendNodeToJson`）原样保留。

## 3. A/B 证据（old 提交版本 vs 新实现）

同一份源码、同一编译参数，**只换头文件**，交替运行取中位数：

* **项目自带 bench**（`bench/bench_main.cpp`，第三方库关闭以排除干扰），5 组交替：

```
op        dataset        old MB/s  new MB/s  speedup
parse     flat_10KB        122.01    157.09    1.29x
parse     flat_100KB       113.39    198.28    1.75x
parse     mixed_10KB       166.36    178.08    1.07x
parse     mixed_100KB      166.38    186.85    1.12x
parse     mixed_1MB        173.22    178.56    1.03x
parse     几何平均 1.228x (+22.8%)
stringify 几何平均 1.013x    copy 几何平均 1.029x
```

* **噪声基线（对照组）**：同一二进制当 A、当 B 各跑 5 组 → parse 几何平均 **1.031×**（运行顺序偏差）。
  因此 parse 的净收益约 **+19% ~ +23%**，取 **+22.8%** 为原始值、**+19%** 为保守值。

* 另一套独立 A/B 工具（同一份旧/新头文件）给出 parse 几何平均 1.265×，对照组 1.031× → 净 1.23×，**与上面一致**。

> 未达标的部分要说清楚：stringify / copy **没有变化**（+1.3% / +2.9%，落在噪声内）。本方案只动了解析期的键索引和查询索引，而 `toString()` 的预遍历、`copy` 的 `cloneChain` 都不走这两张表。要动它们需要报告里排第 4 的"stringify 去掉二次遍历"，本轮未做。

## 5. 本轮发现：一个**既有**内存安全缺陷（与本次优化无关）

在压测过程中 ASan 报出：

```
ERROR: AddressSanitizer: heap-use-after-free
WRITE of size 4 ... std::__1::__libcpp_atomic_refcount_decrement
  #4 ZJSON::detail::StoredString::~StoredString()
  #5 ZJSON::Json::~Json()
  #6 ZJSON::Json::deleteJson()
0x... is located 8 bytes inside of 88-byte region   <- make_shared<StringArena> 的控制块
```

**即为**：`StringArena` 的 `shared_ptr` 控制块被**释放了两次**。

**它先于本次改动存在**：把 `git show HEAD:src/zjson.hpp` 取出、用**同一份探针**在 ASan 下编译运行，报出**完全相同的栈**。
（非 ASan 下旧版退出码 127、新版 SIGSEGV —— 同一个根因，新代码的堆布局让它变成硬崩溃。）

**已排除的可能**（均经实测）：
* 不是解析期引用计数配错——解析刚结束时 `arena.use_count()` **精确等于**"存储字符串数 + 2"，例如 300 键文档 375 + 2 = **377**，5 键文档 6 + 2 = **8**；
* 不是节点被构造两次——`JsonKeyIndex` 不持有任何 `StoredString`；
* 不是重复键路径——bench 数据集没有重复键，`KeepLast` 从未执行。

**现状**：`ctest` 14/14 全绿——**当前测试集覆盖不到这个缺陷**（没有任何用例做约千次大文档的 parse/destroy 循环）；官方 bench 也不触发。复现需要 `plan_probe3c.cpp` 那种"多数据集 × 多次迭代 + 存活文档 + 节点churn"的组合，我未能进一步缩小到更小的用例。

**建议**：这是**优先级高于性能**的后续项。定位手段已具备（ASan 栈 + 已证明的"解析后计数正确"这一约束，可把范围锁死在析构路径 `deleteJson` / `releaseChildren` / 池的双重释放上）。

```bash
# 项目自带 bench（含第三方对比）
cmake --preset clang-rlz && cmake --build build
./bin/bench_zjson.exe --only comparative --csv /tmp/cmp.csv
./bin/bench_zjson.exe --only pool
./bin/bench_zjson.exe --only access
./bin/bench_zjson.exe --only hotspot

# 只看 zjson 的 A/B（old=HEAD，new=工作区）
mkdir -p /tmp/bold /tmp/bnew
sed 's|#include "../src/zjson.hpp"|#include "zjson.hpp"|' bench/bench_main.cpp > /tmp/bnew/bench_main.cpp
cp /tmp/bnew/bench_main.cpp /tmp/bold/bench_main.cpp
cp src/zjson.hpp /tmp/bnew/ ; git show HEAD:src/zjson.hpp > /tmp/bold/zjson.hpp
clang++ -std=c++17 -O2 -pthread -o /tmp/bnew/bench_new /tmp/bnew/bench_main.cpp
clang++ -std=c++17 -O2 -pthread -o /tmp/bold/bench_old /tmp/bold/bench_main.cpp
# 交替运行各 5 次，取中位数；并另跑一组"同一二进制当 A/B"作噪声基线

# 测试
ctest --test-dir build          # 14/14
```
