## 一、必须修复（严重）

### F1. 赋值运算符不保留 `this->brother` —— 迭代中给成员赋值会截断整条链（数据丢失 + 泄漏）

位置：`Json::operator=(const Json&)` 与 `Json::operator=(Json&&)`（含 keepName 分支）。

本轮新增的 keepName 修复保留了键名，但两个赋值运算符仍无条件执行 `this->brother = nullptr`（拷贝）或 `this->brother = rhs.brother`（移动，临时节点 brother 必为 nullptr）。成员节点是容器链上的一环，赋值等于把它从链上摘下来。

实测复现（clang64 / C++17，本轮验证）：

```
Json doc("{\"alpha\":1,\"beta\":2,\"gamma\":3}");
for (auto& [key, value] : doc) value = Json(5);
// 实际结果: {"a":5}        ← beta/gamma 从链上脱落
// 期望结果: {"a":5,"b":5,"c":5}
```

后果三重：
1. **数据丢失**：第一个被赋值的成员之后的所有兄弟成员从文档中消失；
2. **静默**：不报错、不崩溃；
3. **泄漏**：脱落的子树不可达，`deleteJson` 无法到达（本库池永不释放，进程级无害，但逻辑上泄漏）。

`tests/test_api_coverage.cpp:1341` 的用例只改第一个成员（alpha 是链头）并只检查它自身 → **恰好掩盖了本缺陷**。报告中"成员节点整体赋值不再丢键，`for (auto& [k,v] : obj) v = Json(1);` 现在保持键不变"的表述与实际行为不符——该循环实际只会改到第一个成员。

**修复**（与 `overwritePreservingLinks` 同规则，两个运算符各加两行）：

```cpp
Json& operator = (const Json& origin) {
    if (this == &origin) return *this;
    Json* savedBrother = this->brother;      // 成员节点保持链上位置
    ...
    this->brother = savedBrother;
    return *this;
}
// move-assign 两个分支同理；不要再读 rhs.brother
```

修复后须把 1341 行用例加强：整循环赋值后断言 `toString() == R"({"alpha":5,"beta":5,"gamma":5})"` 且 `size`（成员数）不变。

## 二、建议修复（中）

### F2. `remove(key, self, prev)` 三参形态的容器归属仍是错的

重写后的实现把 `frame.container` 固定为 `this`，但当外部调用 `remove(key, self, prev)` 且 `self` 不是 `this->child` 时（历史递归约定：`prev` 是 `self` 的前驱、链属主是别的节点）：
- `unlinkChild` 在 `prev == nullptr` 时改写的是 `this->child` 而非真实属主的 `child`；
- `lastChild` / `keymap` 也在错误的容器上修复。

内部已无此调用路径，但它是公开 API。建议：要么在三参入口直接按"prev 非空则由 prev 推出属主"修正，要么文档标注"三参形态仅供内部/历史兼容，勿用"。低频路径，不阻塞合入。

### F3. 线程驻留池的线程churn 风险需要在 README 写明量化边界

每线程池 + 永不释放 + 无锁的选型有扎实的实测支撑（×2.56~2.94 vs ×0.42~0.47），结论正确。但"每线程按峰值驻留"意味着：**频繁创建/销毁线程的服务模型（每请求一线程）内存无上界增长**。1024 块/slab、~176B/块 ≈ 每 slab 180KB——一个曾解析过较大文档的短命线程也会永久占住这些 slab。
建议：README 线程契约加一条"长生命周期线程池模型下无额外代价；线程频繁生灭的模型请复用线程，或改用共享池构建（可留一个编译开关）"。
