## 二、本轮静态复核备注（低风险，无需行动）

1. `toInt()` 语义微变：整数态走 `numberAs<int>()`（截断规则与旧 `(int)toDouble` 同类，仅实现路径不同），无行为回归。
2. `estimateSerializedSize` 的混合递归（≤512 层递归、超出转帧式）正确；递归/帧式两版的 pretty 估算公式略不同但都只是 reserve 提示，欠估只会导致扩容。
3. 预留量对**含转义字符串**仍可能欠估（原始 size+2 vs 转义后最多 6×/字符）——先于本轮存在，只影响 reserve 精度。
4. `parse(const string&)` 与 `parse(string&&)` 各自完整实现（validateUtf8 块重复 ~15 行）——可提取公共体，纯整洁问题。
5. cloneChain/deleteJson 本轮重写（帧推进先于 push、先于 delete）——深树探针 + ASan 复归通过，帧引用失效风险已规避。

## 三、问题解答

### 3.1 如何在不改接口的前提下靠近 RapidJSON

现状：parse 0.17–0.31×、stringify 0.48–0.53×。差距来源按大小排序：

1. **节点体积（决定性）**：176B vs RapidJSON 16B，11× 的内存带宽/缓存差距。这是 R2（已论证的 StoredString 瘦身路径）。**不做这一步，其它所有优化合计只能拿 20~40%**。目标 176→80~96B（`variant<string_view, owned>` 化 StoredString），预期 parse 单项 1.5~2×，stringify 同步受益（0.48×→0.8×+）。
2. **宽对象索引**（见 3.2）。
3. **解析扫描微优化**：查表跳空白 + memchr 大步扫字符串（RapidJSON 是 SIMD；查表能拿到其一半收益），预期 +5~10%。
4. **stringify 去掉二次遍历**：`toString` 先 estimate 全树再写；可用 arena 源长度做上界提示，省一次 O(n) 预遍历。
5. **远期**：`parse(string&&)` 的 insitu 变体——arena 已拥有缓冲区，转义可原位解码，省掉 chunk arena 拷贝。工程量中等。

务实预期：完成 1+2+3 后 parse 约 0.5~0.7×、stringify 接近持平 RapidJSON。**完全追平 parse 需要节点逼近 16B，这与 StoredString 零拷贝设计冲突**；而 zjson 的保序/Pointer/Patch/错误定位是 RapidJSON 没有的，"parse 快 nlohmann 1.5~2×、功能面更大"的定位本身成立。

### 3.2 开放寻址表替换 unordered_map：代价与收益

先厘清热点在哪——**zjson 解析时 ≤16 键的对象根本不走哈希**（Frame 内 16 槽小索引），受影响的是两处：

| 位置 | 现状 | 换开放寻址后 |
| --- | --- | --- |
| 解析器 keyIndex（>16 键的对象，解析期） | `unordered_map<string_view,Json*>`：每键一次**结点分配** + rehash | 单块平坦数组（2 的幂 + 线性探测，存 {hash, Json*}）：仅 1~2 次表分配，插入约 **2~4×** |
| 惰性 keymap（解析后查询） | `unordered_map<string,Json*>`：每键 1 次 string 分配 + 1 次结点分配 | 键视图指向节点 name，建表约 **2~3×**、查询约 **1.5~2×**（缓存友好、无指针追逐） |

**代价**：
- 代码量 ~120–180 行（含扩容、删除语义——解析索引只在 KeepLast 时失效，可用墓碑或整表作废；keymap 现有纪律本来就是"结构变化即整表作废"，天然契合）。
- **主要风险在键生命周期**：keymap 若改存"指向 node->name 的视图"，必须审计所有改键/删节点路径（现有 unlinkChild/removeDirectChildrenByKey/appendNodeToJson 三处纪律已覆盖，但 `overwritePreservingLinks` 家族要逐一确认不改名）。解析索引无此问题（视图进 arena）。
- 工期估计：1.5~2 天含测试。

**收益（分场景）**：
- twitter.json 这类真实负载：**+3~8% parse**（多数对象 ≤16 键，本来就走小索引）；
- 宽对象文档（数百~数千键的扁平对象）：该路径 **1.5~2.5×**，整文档 parse 视占比可达 +20~40%；
- 首次 `operator[]` 宽对象建表：2~3×。

**结论与建议顺序**：解析器 keyIndex 先换（收益确定、无生命周期风险、改动封闭）；keymap 的键视图化等 R2 节点瘦身一起做（都要动 StoredString/名字生命周期，合并一次审计）。整体优先级仍然低于 R2——节点体积是数量级问题，哈希表是常数问题。

> **已实施（2026-09-15）**：§3.2 的方案经独立探针验证后落地，结果见
> [`docs/性能优化实施与评估-2026-09-15.md`](性能优化实施与评估-2026-09-15.md)。
> 实测与该段估计的差异：
> * keyIndex 的收益被**低估**——它是 flat_10KB 解析的 41.9%，换掉后 parse 几何平均 **+22.8%**，flat_100KB **1.75×**；
> * keymap 的"键视图化"**未按本段做**：改成"槽位只存 {hash, 节点指针}，比较时读 `node->name`"，因此不持有任何视图，**不需要** R2 一起做，生命周期风险归零，且建表+查询实测 **10×** 以上；
> * §3.1 建议的第 4 条（stringify 去二次遍历）**未做**，本轮 stringify 无变化。
> * §3.1 提到的"查表跳空白 / `memchr` 大步扫字符串"经实测在本 bench 数据集上是**负收益**（`memchr` 0.42×），已否决。
> * 另发现一个**既有**（非本轮引入）的 `StringArena` 引用计数双重释放缺陷，详见该文档 §5。
