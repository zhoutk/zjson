## 二、已实施项的细节与验证

### 2.1 §3.3 补丁（P1）

三处改动与复核文档的 diff 逐字一致（move 构造、move 赋值、`borrowed()` 收窄）。合入前我方复核了其安全性边界：

* moved-from 处于 `usingRef=true, arena=null, ref=空` 态——`~StoredString` 对它退化为 no-op（`shared_ptr` 为空、`string_view` 平凡），`view()/str()/strRef()/赋值族/clear()` 在该态下全部安全；
* **必须**同步收窄 `borrowed()`：拷贝一个 moved-from 会得到"借用标记 + 空 arena"的存活对象，不收窄则 `compactReserveHint` 会解引用空 arena——补丁已含，两处一体落地；
* 源对象上不再有任何 placement-new 覆盖（grep 验证：对 `other.payload` 的写只剩 `ref = string_view()`），§五.1 的隐式不变量随之消失。

**复测**：build exit 0；ctest **14/14**；ASan（probe5 深树、probe3c-fixed churn、官方 bench 全节）零报告。
~~A/B（HEAD=0dafae6 vs 补丁后工作区，8 轮交替中位数）：parse 几何平均 0.988——回退回收至 ~−1%~~——**勘误（2026-09-15 验证轮，§五.1）**：0.988 是 `R2（未打补丁）→ R2（已打补丁）` 的比值，被误读为 `c9b4ab7 → 补丁后`。直接对拍 `c9b4ab7 → 补丁后工作区` 得 **0.955×**，与未打补丁的 0.952× 在噪声内一致——**补丁对 parse 中性，R2 的 parse 回退并未由此回收**。补丁以稳健性理由保留（见上表）。

### 2.2 §4.2 钳制（P2）

```cpp
static constexpr size_t maxReserveHint = 4u << 20;
...
return source > maxReserveHint ? maxReserveHint : source;
```

实测 graft 场景（1MB 源文档借出 13B 输出）输出仍逐字节正确；`1e15`×4 的数字增长场景输出 69 字节正确。钳制后该场景的过预留峰值有界（≤4MB），快路径保持 O(1)。

## 三、未采纳项与理由

| 备选 | 不采纳理由 |
| --- | --- |
| §4.2 "按根部直接子节点个数缩放 / 明显失配时回退 estimate" | 两个变体都要先知道子节点规模：要么付一次 O(width) 的 `childCount()` 遍历（宽对象上把这个 O(1) 快路径变成 O(n)，恰在最大的数据集上最疼），要么用"前 16 个兄弟"做密度采样——对"3 个成员各 300KB 长串"这种合法形态会误判回退。钳制以"罕见场景内存峰值有界"换"快路径恒定 O(1) + 零误判"，语义不变。这正是复核文档自己倾向的方案 |
| §4.1 "按数字个数累计余量" | 等价于恢复一次按数字计数的预遍历——与本提示"省掉二次遍历"的目的相抵；欠预留的代价只是 `std::string` 几何扩容，且有 +64 兜底，注释已如实写明 |
| 对 stringify "+1.7% vs +4.9%" 的分歧做进一步测定 | 两读数都在该数据集的噪声带内（本机短时测量离散度已知 6~13%），文档已统一表述为"+1~5%"，再测不产生信息量 |

## 五、独立验证结果（2026-09-15，第三方复核）

验证报告：[`docs/复核验证与遗留问题-2026-09-15.md`](复核验证与遗留问题-2026-09-15.md)。

**已核实的部分**：三处补丁**逐字落地**；`build` exit 0、`ctest` **14/14**、ASan 全量 `ctest` **14/14 零报告**；copy **+15.5%**、stringify **+4.1%** —— 与本文报告一致。`borrowedArena()` 改按值返回属额外加固，方向正确。钳制代价实测 16.6 MB 输出 **+1.3%**，可接受。

**需注意的三点**：

1. **本报告 §2.1 的复测结论（"parse 几何平均 0.988，回退回收至 ~−1%"）基准写错了**。0.988 是 `R2（未打补丁） → R2（已打补丁）`，不是 `c9b4ab7 → 补丁后`。直接测量 `c9b4ab7 → 补丁后工作区` 得 **0.955×（−4.5%）**，与未打补丁的 0.952× 在噪声内一致 —— **补丁对 parse 是中性，回退仍然存在**。
   补丁仍应保留，但理由改为稳健性（消除 moved-from 上 placement-new 覆盖 `ViewPayload` 的隐式不变量，且与 `borrowed()` 收窄必须成对）。
2. **回退的部分归因已找到**：保留联合、仅把 `Json` 补回 176 B，可回收约 **1.8%**（宽对象 5–6%）；即约四成来自**节点跨度变小本身**（更小反而更慢，方向反直觉，机制未证实），其余约 2.7% 未定位。建议做一次 128/144/160/176 的跨度扫描确认。
3. **新发现一个 R2 引入的真实缺陷**：`strRef()` 在抛异常前就翻转了标记并析构了视图，`bad_alloc` 后对象处于"标记自有、无任何 string 存活"态 ⇒ UB（故障注入演示：再次读同一个键返回 `size=1` 的伪串）。修复只需先把字符串物化到局部再搬入联合（多一行），且全类仅此一处有洞。建议补一条"注入分配失败后对象仍可用"的回归测试。

**工程注记（回归测试的可注入性）**：注入依赖测试二进制内对全局 `operator new` 的覆盖能**看见**物化分配。本机 clang64 的 libc++ 以 DLL 形态发行，`std::string` 的 extern-template 实例化驻留 DLL——**-O0 下**其分配绕过可执行文件的覆盖，注入恰好对目标分配失明（倒计时残留，在 gtest 内部分配上引爆，表象为"异常逃出 EXPECT_THROW"）。-O1 及以上构造被内联进测试 TU，注入可靠（-O0/-O1/-O2/-O3 四档实测）。故 `test_exception_safety` 目标在 CMake 中固定 **-O2**，与构建类型无关。排查中曾怀疑"解析后键的借用/自有状态随优化级别变化"，用分配计数器与插桩头文件证伪——库行为确定性无误，纯为注入可见性问题。

**不采纳理由**：
* §3 的 176B 填充/跨度调整：直接回退节点跨度会损失 R2 已实测的 copy +15.5% 等收益；"cache set 冲突"假说未经验证；128/144/160/176 跨度扫描是正确的下一步，属独立测量工作，不在缺陷修复轮内夹带。`sizeof(Json)==128` 的 static_assert 锁不动。
* §4 之外再为 parse −4.5% 做性能收敛：与 128B 跨度同源，等跨度扫描定位后再动。
