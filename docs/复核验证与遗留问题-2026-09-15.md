## 1. 新发现：`strRef()` 的异常安全回退（R2 引入）

### 1.1 代码

```cpp
const string& strRef() const {
    if (usingRef) {
        ViewPayload viewPayload = std::move(payload.view);
        payload.view.~ViewPayload();     // 视图已析构
        usingRef = false;                // 标记已翻转成"自有"
        new (static_cast<void*>(&payload)) string(viewPayload.ref.data(), viewPayload.ref.size());
        //   ^^^ 这一步会分配内存，可以抛 std::bad_alloc
    }
    return payload.owned;
}
```

`usingRef = false` 与视图析构都发生在**可能抛异常的构造之前**。一旦抛出，对象处于"标记说自有、但联合里没有任何 `string` 存活"的状态，此后它的析构函数会对未构造的字节调用 `~basic_string()`。

### 1.2 这是 R2 引入的回退（对比 `c9b4ab7`）

```cpp
const string& strRef() const {
    if (usingRef) {
        if (ref.empty())
            owned.clear();
        else
            owned.assign(ref.data(), ref.size());   // 也可抛
        usingRef = false;                            // 只在成功之后翻标记
        ref = string_view();
        arena.reset();
    }
    return owned;
}
```

旧布局里 `owned` 与 `ref`/`arena` **同时存在**，`owned` 始终是一个活对象：`assign` 抛异常时 `owned` 仍是合法对象、`usingRef` 仍未翻转 ⇒ 对象**保持一致**（可重试）。**联合化把成员互斥化，却没有把"翻标记"挪到构造之后，于是丢掉了这个性质。**

### 1.3 可达性与演示

唯一入口是 `JsonConstEntry::key()` / `JsonConstIterator::key()`（`src/zjson.hpp:4401`、`4418`），即 `for (auto&& e : parsedDocument) e.key();` 这种普通用法；只要被借用的那个字符串大到分配失败就会触发（例如解析一份含超大字段的文档后遍历它）。

**故障注入演示**（`plan`：在 `usingRef = false` 与构造之间注入 `throw std::bad_alloc`）：

```
parsed (isError=0)
caught bad_alloc -> tag already flipped to 'owned', but no string was constructed
reading the same key again: size=1  equals_original=NO (inconsistent object)   <-- 读到伪对象
destroying the document...
```

即：抛异常后**再次读取同一个键会得到一个内容错误的字符串**（`size=1`，与原来的 70 字符键不相等）。

**诚实说明**：我没能让它崩溃——残留字节恰好形似"短字符串"，所以 `~basic_string()` 变成了 no-op，ASan 没有报告；换个堆布局就可能变成非法 `free`。无论哪种表现都是 UB，"静默读到错值"甚至更难发现。

### 1.4 建议修复（多一行）

先把字符串物化到局部，再搬进联合——`string` 的移动构造是 `noexcept`，于是抛异常时对象仍保持一致：

```cpp
const string& strRef() const {
    if (usingRef) {
        ViewPayload viewPayload = std::move(payload.view);   // 期间 arena 仍被持有
        string materialized(viewPayload.ref.data(), viewPayload.ref.size());  // 可能抛：对象尚未被改动
        payload.view.~ViewPayload();
        usingRef = false;
        new (static_cast<void*>(&payload)) string(std::move(materialized));   // noexcept
    }
    return payload.owned;
}
```

同类位置我逐个查过，**只有这一处**有洞：`makeOwned()` / `clear()` 里的 `new string()` 是默认构造（不分配，`noexcept`）；两处 `new ViewPayload(...)` 的拷贝/移动构造均为 `noexcept`。

## 2. 撤回我上一轮的机制结论（重要）

我在《复核-2026-09-15-R2与UAF归因》§3.3 写过："补丁把 parse 从 **0.952× 回收至 0.990×**，机制确认"。**这个说法错误**，原因是我把两次不同基准的测量串在了一起：

| 测量 | 基准 → 对象 | 顺序修正后 parse 几何平均 |
| --- | --- | --- |
| `r2_ab` | `c9b4ab7` → R2（**未打补丁**） | 0.952 |
| `pv_ab` | R2（未打补丁） → R2（**已打补丁**） | 0.993 |

0.952 与 0.990/0.993 **不是同一条链上的两个点**，不能读成"从 0.952 改善到 0.990"。把它们相乘得到 0.942，而**直接测量** `c9b4ab7` → 当前工作区（已打补丁）得到：

| 数据集 | `c9b4ab7` | 当前工作区 | 比值 | 对照 |
| --- | ---: | ---: | ---: | ---: |
| parse flat_10KB | 152.24 | 137.44 | 0.903× | 1.006× |
| parse flat_100KB | 192.76 | 180.79 | 0.938× | 0.998× |
| parse mixed_10KB | 176.73 | 172.86 | 0.978× | 0.994× |
| parse mixed_100KB | 182.83 | 179.58 | 0.982× | 1.012× |
| parse mixed_1MB | 168.66 | 168.16 | 0.997× | 1.014× |
| **parse 几何平均** | | | **0.955×** | 1.005× |

**结论：补丁对 parse 中性（0.952 → 0.955，噪声内），它并没有修回 R2 的 parse 回退。**

这正是我在同一份文档里批评报告"flat_100KB +9%"时犯的同一类错误（比值串基准）。教训：**每一条比值都要写清 A 与 B 各是什么**；把两次独立 A/B 的比值相乘做推断前，必须先确认它们首尾相接。

补丁仍然值得保留，但理由要改成稳健性而非性能：

* 消除"在 moved-from 对象上 placement-new 覆盖 `ViewPayload` 而不先析构"的隐式不变量（复核 §五.1）；
* 与 `borrowed()` 收窄**必须成对**——拷贝一个 moved-from 会得到"借用标记 + 空 arena"的活对象，不收窄则 `compactReserveHint` 解引用空 arena。你的处置把这两件事一起落地了，这点是对的。

## 3. parse 回退的部分归因（新证据）

既然补丁不是原因，我做了隔离实验：**保留标记联合，只把 `Json` 用尾部填充补回 176 B**（节点跨度与池块大小恢复旧值，联合代码不变）。

| 项 | 176 B（填充） | 128 B（当前） | 比值 | 对照 |
| --- | ---: | ---: | ---: | ---: |
| parse flat_10KB | 154.90 | 146.40 | 0.945× | 1.005× |
| parse flat_100KB | 193.01 | 184.01 | 0.953× | 0.996× |
| parse mixed_10KB | 174.41 | 170.17 | 0.976× | 0.996× |
| parse mixed_100KB | 182.46 | 179.05 | 0.981× | 0.981× |
| parse mixed_1MB | 175.74 | 179.41 | 1.021× | 0.986× |
| **parse 几何平均** | | | **0.975×** | 0.993×（修正后 0.982×） |

**读数**：把跨度补回 176 B 可回收约 **1.8%**（几何平均），在宽对象数据集上回收 **5–6%**。也就是说：

* 约**四成**的 parse 回退来自**节点跨度变小本身**——方向反直觉：**更小的跨度在宽对象上更慢**。
  最可能的机制是 stride 从 176（=2.75×64，非 2 的幂）变成 128（=2×64，2 的幂）后，宽对象哈希索引的指针追逐落在固定的 cache set 上产生冲突未命中。**这只是推断，我没有验证**。
* 剩余约 **2.7%** 仍在联合代码内部（联合后的 `view()` 分支、`fromView` 的构造序列、`Frame` 因 `StoredString` 变小而改变等），**未定位**。

**建议**：若要把回退彻底关掉，下一步做一次"跨度扫描"——在 128/144/160/176 之间各测一遍 parse，看是否在非 2 的幂处出现拐点。这能把"cache set 冲突"从推断变成结论，并且可能找到一个既有小跨度、又不踩冲突的折中（例如把 `blocksPerSlab` 或对齐改成非 2 的幂）。

## 4. 4 MB 钳制：代价实测（可接受）

对 16.6 MB 输出、6 组交替：

| 方案 | `toString()` 中位数 | 区间 |
| --- | ---: | ---: |
| 当前（钳到 4 MB） | 16.469 ms | 16.236 – 16.552 |
| 变体（超界回退精确预遍历） | 16.258 ms | 16.115 – 16.336 |

**钳制代价 +1.3%**（跳过了预遍历，但要额外几次扩容拷贝）。可控，`正确性` 两者都逐字节正确。若想再省这 1.3%，把

```cpp
return source > maxReserveHint ? maxReserveHint : source;
```

改成

```cpp
return source > maxReserveHint ? 0 : source;   // 让 toString() 走 estimateSerializedSize
```

即可：4 MB 以下仍是 O(1) 快路径；4 MB 以上改为一次精确遍历（这本就是 R2 之前的做法），既不会欠预留也不会过预留；graft 场景只遍历那棵小树，代价极小。**这不改变语义，属可选微优化**——你选的钳制方案本身没有问题，把上界收在 4 MB 的取舍是合理的。

## 5. 其它（非缺陷，建议顺手清理）

1. **`borrowed()` 上方有一段重复注释**：旧的 3 行注释没有删掉，新的 5 行接着它，读起来像两句重复的话（`src/zjson.hpp:320` 附近）。
2. **`compactReserveHint()` 与 `maxReserveHint` 是 public**（其前最近的访问说明符是 2045 行的 `public:`）。`compactReserveHint` 是 `toString()` 的内部序列化辅助，暴露它扩大了 API 面；`maxReserveHint` 也是本次新增的公开常量。建议移入 `private:`（R2 提交即如此，本次未变）。
