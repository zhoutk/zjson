# 多线程使用指南

> 本文回答三个问题：**哪些用法本来就安全**、**第三方「自己加个锁」够不够**、**推荐的几种模式各要花多少钱**。
> 配套证据：[`线程安全审查与修复-2026-09-16.md`](线程安全审查与修复-2026-09-16.md)（两个只读竞态的定位与修复、A/B 性能数据）。
> 本机实测数据来自 clang64（clang 22.1.8 / libc++ / x86-64 / `-O2`），`sizeof(Json)=128`。

---

## 0. 结论先行

| 场景 | 是否安全 | 需要做什么 |
|---|---|---|
| 每线程各自持有、各自使用的文档（parse / 增删改 / 序列化） | ✅ 安全 | 什么都不用做（实测 4 线程扩展 ×2.86） |
| 一棵**只读**的树被多线程共享（含 `key()`/迭代/`toString`/深拷贝/`==`） | ✅ 安全 | 只需保证「发布」这个动作有同步（见 §3.5） |
| 节点跨线程分配/释放（含分配线程已退出） | ✅ 安全 | 什么都不用做（每线程池 + 永不释放） |
| 一棵**边读边写**的树 + 外部加锁，且**只用值语义 API** | ✅ 安全 | 见 §3.2 的白名单，缺一不可 |
| 一棵**边读边写**的树 + 外部加锁，但用了 `atRef`/`findPtr`/迭代器/`JsonEntry::value()` | ❌ **不安全** | 锁救不了，必须改成值语义或改用 §4 的快照模式 |
| 把 `Json*`/`Json&` 交给别的线程却没有任何同步 | ❌ 数据竞争 | 即使此后无人写也要有 release/acquire |

一句话：**锁能让「值语义」的并发读写变安全，不能挽救「把内部引用/指针带到锁外面」的用法。**

## 1. 库内部的并发设计（为什么只读安全）

只读安全不是「运气好」，而是三条设计共同保证的。理解它们有助于判断边界在哪。

### 1.1 节点池：每线程、无锁、永不释放

`detail::SlabAllocator<sizeof(Json)>` 是 `thread_local` 的，每个线程只操作自己的池，**全程无锁**。
slab 从不归还给系统，所以「A 线程分配、B 线程释放」（甚至 A 已经退出）都安全——不需要任何同步。

代价（必须知道）：

- **驻留按线程峰值保留**：实测 64 个短命线程各自解析 4 万节点，进程永久增长约 440 MB。**请复用工作线程**，不要「每请求一线程」。
- 跨 DLL 传递文档并在拥有模块卸载后析构是不安全的（池是模块内 `thread_local`）。

### 1.2 惰性键索引：原子 CAS 发布

`operator[]`/`contains`/`findPtr`/`at`/`atRef` 会用到对象成员的哈希索引。首次查询时由**读线程自己**构建，再用
`compare_exchange_strong` 发布；竞争失败的线程**直接使用赢家建好的那张表**（描述的是同一条链，无需重试）。

因此：

- 多个读线程并发首次查询同一对象是安全的（实测：8 线程 × 60 轮共享新解析的文档，ASan 无报告）。
- 相对早期实现（每线程都 `delete` + `new` 同一张表）这里是曾经的 `heap-buffer-overflow`，修的就是它。
- 代价只有命中路径上的一次 acquire load（x86-64 上就是普通 MOV）。

### 1.3 没有任何 const 读路径会写节点

这是最关键的一条，也是 2026-09-16 修订的重点：

- `JsonEntry::key()` / `JsonConstEntry::key()` / `JsonIterator::key()` / `JsonConstIterator::key()` 返回
  **`std::string_view`**，直接指向节点里已有的字节，**不物化、不分配、不可能抛异常**。
- 历史实现里 `key()` 返回 `const string&`，对「借用」的键名必须**就地改写**节点（析构 view → placement-new 一个
  `std::string` → 翻转 tag）。两个读线程同时对同一节点调用 `key()` 就是对同一个 union 并发析构/构造。
- 那个物化函数（`StoredString::strRef()`）**已被删除**，不是「不再调用」——所以「只读不写」是结构性保证，而不是
  靠约定维持。**请不要把它加回来**。

## 2. 逐场景的正确用法

### 2.1 每线程一个文档（最常见，也最省事）

```cpp
std::vector<std::thread> workers;
for (int t = 0; t < 4; ++t) {
    workers.emplace_back([t] {
        std::string err;
        Json doc = Json::ParseJson(requestText(t), err);   // 自己的文档
        doc.add("worker", t);
        doc.remove("unused");
        std::string out = doc.toString();
        // ... 使用 out
    });   // 线程退出：池驻留、文档析构，都安全
}
```

无需任何同步。**这是默认应该选择的形态。**

### 2.2 跨线程移交所有权（生产者建、消费者改）

构建线程退出后，另一个线程继续修改和释放，是安全的：

```cpp
Json document;
std::thread producer([&] {
    Json local(JsonType::Object);
    for (int i = 0; i < 500; ++i) local.add("k" + std::to_string(i), i);
    document = std::move(local);      // 节点来自生产者线程的池
});                                    // 生产者线程结束后……
producer.join();
document.add("extra", 1);              // ……消费者线程照样能增删
```

这是 `test_thread_safety.cpp` 的 `nodes_may_be_allocated_and_released_on_different_threads` 用例。

> 注意：`document = std::move(local)` 与随后的 `join()` 已经建立了同步边，所以安全。
> **不要**把一个普通（非原子）`Json*` 交给另一个线程却不做同步——见 §3.5。

### 2.3 一棵只读的树被多线程共享

这是本次修复后才成立的用法，可以放心用：

```cpp
const Json& shared = parsedDocument;       // 之后不再有人修改它（唯一前提）
// 每个线程都可以做：
//   shared.contains("k") / shared["k"] / shared.findPtr("k") / shared.at("/a/b")
//   shared.atRef("/a/b")                // 只读引用，只在本线程内使用
//   for (const auto& [k, v] : shared) ...   // 含 k（string_view）
//   shared.toString() / Json copy = shared; / copy == shared
```

关键是**「之后不再有人修改」**：并发读写仍然不安全（见 §3）。

> 头文件末尾的**辅助块**（`directChild`/`hasChild`/`childValueOr`/`ownedKey`/`memberCount`/`isEmptyObject`/
> `setElement`/`setChild`）在只读共享下同样是安全的，但其中 `directChild` 返回**指针**、`setChild`/
> `setElement` 是**写**操作——跨线程用时的取舍见 §3.1/§3.2。背景与用例见
> [`使用指南.md`](使用指南.md) §8。

### 2.4 快照发布 / 订阅（读多写少的推荐模式）

见 §4.4：写者复制→改副本→原子发布，读者拿快照。读侧完全无锁、无争用。

## 3. 「第三方生成和修改时加个锁」——够还是不够？

**结论：视 API 用法而定。** 只有一个条件成立时，加锁才是充分且高效的：

> **任何指向树内部的引用/指针都不允许活过临界区。**

### 3.1 为什么「锁保护不了引用」

锁只能保护**临界区内部**的访问。而下面这些 API 会把树的内部地址**交到临界区之外**：

| API | 交出什么 | 后果 |
|---|---|---|
| `atRef(pointer)` | `const Json&` | 解锁后写者 `add`/`remove` 可能释放该节点 → 悬垂引用 |
| `findPtr(key)` / `findPtrAt(pointer)` | `Json*` / `const Json*` | 同上，且可变指针可以被写者之外的逻辑改坏 |
| `directChild(object, key)`（**末尾辅助块**） | `const Json*` | 同上。**最容易忽略的一个**：它名字像「取值」，实际返回的是指向文档内部的指针。需要跨临界区留用请改用 `childValueOr`（返回值） |
| `directMemberPtr(key)`（`Json` 的公开成员） | `const Json*` | 同上；`directChild` 就是它的薄包装 |
| `begin()` / `end()` / `cbegin()` / `cend()` | 持有 `Json*` 的迭代器 | 迭代期间写者改链表 → 迭代器失效 |
| `JsonEntry::value()` / `JsonConstEntry::value()` | `Json&` / `const Json&` | 同上 |
| `key()`（四个重载） | `std::string_view` | 键名可能借自文档的 arena（**长键**）→ 解锁后视图本身仍指向已释放的 arena |
| `remove(key, self, prev)` 三参形式 | 收 `Json*` 游标 | 同上 |

所以「加锁」这件事本身没问题，问题是**这套 API 的形状**：只要有一个引用逃出去，锁就形同虚设，
而且不会有任何编译期或运行期提示。

### 3.2 加锁方案的白名单（缺一不可）

若要用 `/外部加锁` 的方式支持并发读写，必须同时满足：

1. **写**：`add`/`remove`/`take`/`clear`/`operator=`/`setAt`/`applyPatch`/`mergePatch`/`push_back`/`push_front`/`insert`/`pop_back`，以及辅助块里的 `setChild`/`setElement`，全部在同一把锁下。
2. **读**：只使用**返回值**的 API——
   `operator[]`、`at`、`contains`、`try_get`/`try_int`/`try_double`/`try_string`、`getAllKeys`、`toVector`、`size`、
   `isXxx`、`toInt`/`toDouble`/`toInt64`/`toUint64`/`toString`/`dumpTo`、`operator==`，
   以及辅助块里的 `hasChild`/`childValueOr`/`memberCount`/`isEmptyObject`/`ownedKey`。
   它们返回副本或标量，天然可以带出临界区。
3. **禁止**在锁外使用 `atRef`/`findPtr`/`findPtrAt`/`directChild`/`directMemberPtr`/`begin`/`end`/`value()`/`key()` 的结果；
   锁内用完即弃（`key()` 的 `string_view` 若要留用，必须**在锁内**转成 `std::string`，或用 `ownedKey()`）。
4. 锁必须是**同一把**，且覆盖**所有**触及该树的代码路径。

不满足条件 3 是最容易犯的错，因为它在单线程测试里完全看不出问题：

```cpp
// ❌ 错的：引用带出了临界区
const Json* member;
{ std::shared_lock g(mutex); member = doc.findPtr("conf"); }
{ std::unique_lock g(mutex); doc.add("other", 1); }     // 可能移动/释放 conf 相关节点
int v = member->toInt();                                // 悬垂，UB

// ✅ 对的：锁内取值
int v;
{ std::shared_lock g(mutex); v = doc["conf"].toInt(); } // 返回的是副本

// ✅ 也可以：用值语义的辅助函数把指针留在锁内
bool has;
{ std::shared_lock g(mutex); has = ZJSON::hasChild(doc, "conf"); }
```

> **`setChild` 的额外注意**：它为了「替换而不留重复成员」会**重建整个对象**再整体赋值
> （`object = replacement`），因此它**替换掉了所有节点** —— 任何在它之前取得的引用/指针/迭代器
> （无论在不在锁内）都会失效。多线程下它必须与所有读一起置于同一把锁下。

### 3.3 锁该加在哪、什么时候不需要加

- **「生成」阶段通常不需要锁**：每个线程构造自己的 `Json`，天然隔离（§2.1）。
- **只有在「把一棵可变的树共享给多个线程」时才需要锁**（或改用 §4 的模式）。
- 若走「加锁」路线，`std::shared_mutex`（多读者/单写者）比 `std::mutex` 更贴合读多写少，但请先看 §4.1 的实测数字——
  它在争用时可能比你想的贵得多。

### 3.4 加锁方案能拿到多少并发？

**拿不到「并行读」。** 一个文档级锁意味着所有读者争用同一条 cache line：

| 操作 | 本机实测 |
|---|---|
| `contains()` 命中（本库，无锁） | **4.05 ns** |
| `findPtr()` 命中 | 3.67 ns |
| 一把 `std::shared_mutex` 的 `lock_shared+unlock`（无争用） | 21.6 ns |
| 4 线程争用**同一把** `shared_mutex` 的共享锁 | **258 ns / 次** |
| 4 线程各用**自己**的锁（对照组） | 30.8 ns / 次 |
| 4 线程争用同一把 `std::mutex` | 96.1 ns / 次 |

也就是说：加锁后每次读从 4 ns 变成 21.6 ns（无争用）到 258 ns（4 读者），**4 个读者比各自独立慢 8.4 倍**——
并行读被这把锁退化成串行。**这是「加锁方案」的固有上限，不是本库的实现问题。**

### 3.5 即使只读，发布动作也需要同步

「只读安全」指的是**读到的东西**没问题；但**让别的线程看得见这份数据**仍然需要一条 happens-before 边。

```cpp
// ❌ 错的：普通指针 + 无同步 = 数据竞争（即使此后没人写）
Json* g_document = nullptr;
std::thread reader([&] { while (!g_document) {} g_document->contains("k"); });
g_document = &doc;                       // 写者只是「赋值」

// ✅ 对的：release/acquire
std::atomic<Json*> g_document{nullptr};
std::thread reader([&] {
    while (!g_document.load(std::memory_order_acquire)) yield();
    g_document.load(std::memory_order_acquire)->contains("k");
});
g_document.store(&doc, std::memory_order_release);
```

用 `std::thread` 的构造/`join()`、`std::mutex`、`std::atomic`、`std::promise` 等任何一种方式建立这条边都可以；
关键是**别用裸指针 + 裸标志位**。

## 4. 四种模式与它们的价格

| 模式 | 接口改动 | 内存 | 读成本 | 写成本 | 适用 |
|---|---|---|---|---|---|
| ① 每线程独占（§2.1） | 无 | 每线程一份 | 4 ns（无锁） | 无 | 默认 |
| ② 移交所有权（§2.2） | 无 | 一份 | — | 无 | 生产者/消费者 |
| ③ 外部加锁（§3.2） | 无，但要放弃内部引用类 API | 无 | 21.6~258 ns | +10~23 ns | 写很少、读者也很少 |
| ④ 快照发布（§4.4） | **有**（见下） | 每次写一份新树 | ≈1 ns 原子 load | 一次深拷贝 | 读多写少 |

### 4.1 为什么「库内加锁」这条路走不通

把锁放进库里，成本会比「外部加锁」高得多，而且治标不治本：

1. **锁没有安放处**：`Json` 既是根也是**每个节点**。文档级锁要靠新类型（`JsonDocument`）承载；放进 `Json` 则是
   `sizeof(Json)` 128 → 160（`std::shared_mutex` 实测 32 字节），**每节点 +25% 内存**。
2. **仍然要删掉内部引用类 API**（§3.1），否则锁保护不了逃出去的引用。
3. **每个节点一把 mutex 更糟**：+25~30% 内存，写一个成员要动 3 个节点（前驱、自身、拥有者）→ 锁序与死锁复杂度，
   遍历还要 lock coupling。

所以：**库不提供内建同步，与 `std::string` / `std::vector` / `nlohmann::json` / RapidJSON 的定位一致。**

### 4.2 快照发布/订阅（推荐给「读多写少」）

```cpp
// 共享的是 shared_ptr<const Json>，不是一个可变的树
std::shared_ptr<const Json> g_current;

// 写者（同一时刻只允许一个写者；通常就是那个负责更新的线程）
void publish(const std::function<void(Json&)>& mutate) {
    auto next = std::make_shared<Json>(*std::atomic_load(&g_current));  // 深拷贝
    mutate(*next);
    std::atomic_store(&g_current, std::shared_ptr<const Json>(next));   // 原子发布
}

// 读者（任意线程、任意数量、完全无锁）
auto snap = std::atomic_load(&g_current);
int v = (*snap)["k"].toInt();      // 快照在 snap 存活期间不可变，随便读
```

特点：

- 读者**无锁、无争用、无失效问题**，快照在 `snap` 有效期内是一份普通只读文档。
- 每次发布付一次深拷贝的价钱（见 §4.5）；写者仍然需要外部串行化（写者通常只有一个）。
- **接口上**：`g_current` 的类型变了、生命周期由 `snap` 管理；`atRef` 之类的引用只能在 `snap` 存活期内使用。
  这是「真正解决并发读写」所必须付出的接口代价。

### 4.3 反模式清单

- ❌ 把 `atRef`/`findPtr` 的引用或指针存到临界区外面（§3.2）。
- ❌ 把 `key()` 的 `string_view` 存到临界区外面（长键时它指向文档 arena）。
- ❌ 用非原子的 `Json*` + 标志位跨线程发布文档（§3.5）。
- ❌ 「同一棵树读多写少，所以只给写加锁」——读侧同样要拿锁（或改用 §4.2）。
- ❌ 用 `Json&` 在线程之间共享「同一个根对象」（`Json` 不是引用计数容器）。
- ❌ 每请求创建一个线程并解析大文档（池驻留不回收，见 §1.1）。

### 4.4 各模式的操作成本速查

| 量 | 实测值 |
|---|---|
| `sizeof(Json)` | 128 B |
| 深拷贝一棵树 | **13.5 ns/节点**（短键）；64 字节键 **16.8 ns/节点** |
| 例：12 000 节点文档的深拷贝 | ≈162 µs |
| 例：1 MB（≈108 000 节点）文档的深拷贝 | ≈1.5–1.8 ms |
| `contains()` 命中 | 4.05 ns |
| 原子 load（acquire） | <1 ns |

## 5. 已知限制（无法在不改接口的前提下解决）

1. **同一棵树的并发读写不安全。** 见 §3、§4.1。这是容器定位的必然结果。
2. **池驻留按线程峰值不回收。** 复用线程；不要在请求路径上创建线程。
3. **跨模块（DLL）卸载**：文档跨 DLL 传递并在拥有模块卸载后析构不安全。
4. **解析嵌套上限 101 层**（`cloneChain`/`deleteJson`/打印/比较是迭代实现，20000 层的程序构造文档没问题）。
5. `atRef()` 未命中时返回的是**每线程**的错误哨兵（`thread_local`），所以两个线程不会看到彼此的哨兵，
   但也不要通过它写数据（它是 `const`）。

## 6. 怎么验证你自己的用法

1. **ASan 复现器**：`tools/race_probe_concurrent_read.cpp`（两个 mode 分别对应历史上的两个只读竞态）。
   用法：先用**修复前**的提交编一份看到 ASan 报错，再用当前头文件编一份看到干净——**成对才有证据价值**。
   ```bash
   clang++ -std=c++17 -O1 -g -fsanitize=address -pthread -I<header-dir> \
           tools/race_probe_concurrent_read.cpp -o probe
   ./probe 0 60 8 4000      # 键索引竞态
   ./probe 1 40 8           # 键名物化竞态（键长刻意超过 inline 阈值）
   ```
2. **回归套件**：`tests/test_thread_safety.cpp`（4 个用例）——并发只读、并发 `key()`（同时覆盖
   内联 owned 与 arena 借用两种键名存储）、跨线程分配/释放、独立文档并行。
   ```bash
   ctest --test-dir build -R test_thread_safety
   ```
   辅助块自身的语义（含 `directChild` 的直系语义、`setElement` 的兄弟存活、`setChild` 的去重）由
   `tests/test_util.cpp` 锁定；Qt 关键字宏共存由 `tests/test_qt_macro_compat.cpp` 锁定。
   全量回归：`ctest --test-dir build`（当前 **18/18**）。
3. **性能**：单进程只跑一个小节并交替 A/B，先跑同二进制对照量化噪声。
