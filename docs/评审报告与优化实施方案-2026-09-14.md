### 1.3 本轮已交付的修正（对应原报告 R1，已实施并回归）

1. **`SlabAllocator` 分配配对**：新增 `deallocate(void*, size_t)`，超大块回退 `::operator delete`，不再被当作小块复用（A1）。
2. **`remove(key)` 重写**：显式栈（迭代、无递归）先序删除所有同名**对象成员**；用真实前驱修链、修 `lastChild`、失效父节点 `keymap`；不再触碰数组元素（A2）。**保留"深层删除"语义**——因为 `tests/test_object.cpp` 明确依赖它（`sub20.remove("music")` 删的是嵌套键），原报告建议的"只删直层"会破坏既有契约。
3. **数值解析 locale 无关化**：`std::strtod` → `std::from_chars`（`detail::parseDouble`），仅溢出/下溢回落 strtod，保持 `1e999` 等极端输入仍被接受（JSONTestSuite `i_` 用例已锁定该行为）（A3/A8）。
4. **`toDouble()` 走字符串**：`atof(toString())` → 直接在 `string_view` 上 `from_chars`（少一次分配 + locale 安全）。
5. **`extendItem`**：补 `break`；容器子树改为**移动语义**（`std::move(*cur)`），`extend/concat` 不再重复深拷贝（A5）。
6. **`indexOf`**：去掉每元素 `toString()` 分配与死变量 `Json rs`，改为按叶子文本直接比较（字符串零分配，数字 SSO）。
7. **头文件卫生**：`static` 自由函数 → `inline`；`TYPENAMES` → `inline constexpr const char*[8]`；`max_depth` → `inline constexpr`；补齐 `<cctype> <cstdint> <climits> <cstdlib> <limits>`；`Json(JsonType)` 初始化 `valueNumber`（A8）。
8. **迭代器 STL typedef**：`iterator_category/value_type/difference_type/pointer/reference`（A6）。
9. **新增修正（原报告未提及）**：
   - `Json(Json&&)` 不再继承 `rhs.brother`；`appendNodeToJson` 入链前清空 `node->brother`（否则移动子树会把源链"嫁接"进目标容器，造成别名/环/悬垂——本轮性能优化一度触发了这个潜伏缺陷，测试当场抓出）。
   - 空键（`""`）全链路一致：`add("",v)`、`operator[]("")`、`contains("")`、`buildKeymap`、`getAllKeys`、`remove("")`、`at("/")` 行为统一（此前 `add("")` 会静默丢键、`buildKeymap`/`getAllKeys` 会跳过空键，`extend` 解析结果时**丢数据**）。
   - `insert(index == size)` 改为追加（此前静默无操作），`index > size` 仍保持无操作。
   - `parse()` 入口清空 `err`，成功解析后不再残留旧错误文本。
   - 成员节点整体赋值保留键名：`for (auto& [k,v] : obj) v = Json(1);` 不再把键变成 `""`。
     **【2026-09-14 更正，见 §9.1】** 本条当时的描述“整棵文档保持完好”是**错的**：赋值运算符还会清掉节点的 `brother`，把成员从链上摘下来，导致**除最后一个成员外全部丢失**（对象与数组都中）；当时的验证用例只改了**第一个**成员，因此**掩盖**了该缺陷。现已修复并补上能看见它的回归用例。
10. **节点池最终形态 + LSAN 豁免**：在合并上游 `24189fd` 后，用 `bench/` 实测确认"共享池 + mutex"不可接受（4 线程扩展比 ×0.42~0.47），改为**每线程池 + 永不释放 + 无锁 + 编译期块大小**（×2.56~2.94），并在头文件与 CI 两处实现 LSAN 显式豁免。详见 §8.6。

## 2. 问题清单（复核后）

### 2.1 正确性 / 内存安全（按复核后的严重程度排序）

**A1. `SlabAllocator::deallocate` 无法识别超大块** — 成立（潜在堆损坏）
`allocate(size)` 对 `size > blockSize` 走 `::operator new`，而 `deallocate(void*)` 一律压回小块空闲链。当前唯一分配尺寸恒定（`sizeof(Json)`）故不可达，但是埋雷。
**已修**：改用带尺寸释放（编译器对 class-specific 释放优先选 `operator delete(void*, size_t)`）。

**A2. `remove(key)` 链表修复错误（严重，已修）**
实测该函数在三类形态下都会破坏文档：（a）被删节点的**前驱是容器节点**时，代码按 `pre->type` 判断该改 `pre->child` 还是 `pre->brother`，于是把前驱容器的孩子链整条替换掉（子树泄漏 + 被删节点仍挂在链上 → **use-after-free**）；（b）被删节点是**嵌套容器的首个子节点**时，续扫指针 `pre->brother->brother` 会跳到**另一条兄弟链**上，继续误删并改写无关链；（c）嵌套容器的 `lastChild` 从不修复，删除后该容器再 `add` 会**写穿已释放内存**。复现程序在（a）下直接 `SIGSEGV`。
**已修**：迭代先序删除（无递归），真实前驱修链，`lastChild` 与 `keymap` 同步维护，只在对象成员间匹配键名。
**与原报告的差异**：原报告建议"该函数只应操作直接子层（与 `removeDirectChildrenByKey` 二选一）"。**此建议不可取**——`tests/test_object.cpp` 依赖 `remove(key)` 的深层语义（`sub20.remove("music")` 删掉的是 `sub3` 内部的键）。本版保留深层语义并修正实现。

**A3. 数字解析依赖 locale** — 成立（已修）
`std::strtod` 受 `LC_NUMERIC` 影响：在小数点为逗号的 locale 下 `"1.5"` 会被解析成 1。注意**纯整数不受影响**（不涉及小数点）。已改用 `std::from_chars`（locale 无关），极值回落 strtod 以保留既有"巨指数可接受"的行为。

**A4. 64 位整数精度丢失** — 成立（未修，列入 R5）
实测：`9007199254740993` → `9007199254740992`；`9223372036854775807` → `9223372036854775808`（double 舍入）。长期演进建议补三态 Number（int64/uint64/double）。

**A5. `extendItem` 缺 `break`** — 成立（已修）
补 `break`；`extend(Json)`/`concat(Json)` 的容器子树从"深拷贝"改为"移动"。**更正原报告表述**：这里不是"平方级深拷贝"，而是"参数按值 1 次深拷贝 + 每个容器子节点再来 1 次深拷贝"，量级约为 2 倍而非平方；真正接近平方的是它内部调用的旧 `remove()`（每键一次全树深搜）。

**A6. 迭代器缺 STL typedef** — 成立（已修）。

**A7. `StoredString::strRef()` 的 mutable 惰性物化非线程安全** — 成立（未修，文档明示）
补充：`buildKeymap()` 同为 `const` 方法里的 mutable 写入，多线程**只读**共享同一棵树时会双重构建/双重 delete → UAF。结论必须写进文档：**本库不是线程安全库**（与 nlohmann 定位一致），且"并发只读同一棵树"在当前实现下也不安全。

**A8. 小问题（均已修）**
`Json(JsonType)` 未初始化 `valueNumber`；头文件内 `static` 自由函数导致每 TU 一份副本；`TYPENAMES` 动态初始化；`at()/applyPatch` 大量 `substr` 临时对象（未改，R3）；`equalsObject` O(n²) 配对（未改，R3；注意需保留**重复键的多重集语义**）；`indexOf` 每元素 `toString()`（已修）；`toDouble()` 走 `toString()`+`atof`（已修）。

**A9. 【新增】`Json(Json&&)` 窃取源节点的 `brother`** — 严重（已修）
移动构造会把 `rhs.brother` 一并搬进新节点。当被移动的节点来自某个容器成员时，新节点就把**源文档的兄弟链**带进目标容器：随后 `appendNodeToJson` 不会清空新节点的 `brother`，于是两条链被"嫁接"，出现别名/环；若源节点随后被删（`extend` 循环里就会发生），就是 use-after-free + 无限循环。本轮把 `extend` 改成移动语义后，测试以"挂死 + 输出环状 JSON"的形式当场暴露。已修（移动后 `brother = nullptr`，入链前再清一次）。

**A10. 【新增】空键处理不一致导致数据丢失** — 中等（已修）
`add(name,v)` 在对象上要求 `!name.empty()`（静默丢键）；`buildKeymap`/`getAllKeys` 跳过空键；`operator[]("")`/`contains("")` 直接返回 Error/`false`。后果：**解析得到的 `{"":...}` 一旦经过 `extend`/`Json{{"",...}}` 等路径就会静默丢成员**。已统一为"空键是一等公民"。

**A11. 【新增】`insert(index == size)` 静默失败** — 中等（已修）
原实现循环退出条件导致**在尾部追加时什么都不做**（注释却写"inserted at tail"）。已修：`index == size` 追加，`index > size` 无操作。

**A12. 【新增】大数字溢出后序列化成 `null`** — 低（保留，文档明示）
`1e999` 解析为 `+Inf`，序列化时按 RFC 8259 写成 `null` → 往返丢数据。这是既有设计（`NaN/±Inf → null`）且被 JSONTestSuite `i_` 用例锁定，本版不改，仅在文档中明示风险。

**A13. 【新增】嵌套深度上限实测为 101（文档写 100）** — 低
`parse_json_pda` 的检查在 `push_back` 之前判定 `stk.size() > max_depth`，因此允许 101 层。实测 101 接受、102 拒绝。文档已更正；如需严格 100 层需改判定（属行为变更，另行决定）。

**A14. 【新增】程序化构造深树的递归上限** — 中（列入计划）
解析器深度受 101 限制，但**用户自建**的深树没有限制，而 `cloneChain`/`deleteJson`（子链方向）/`serializePretty`/`estimateSerializedSize` 都是递归。实测：6000 层正常，8000 层在 `cloneChain` 爆栈崩溃。

**A15. 【新增】成功解析后 `err` 残留旧消息** — 低（已修）
`parse()` 只在失败时写 `err`，成功时不动 → 调用方若复用 `err` 变量会误读陈旧错误。已改为入口清空。

**A16. 【新增】通过迭代器 entry 整体赋值会丢键** — 中（已修）
`for (auto& [k,v] : obj) v = Json(1);` 会把成员键变成 `""`（因为键是节点自身状态，赋值被整体覆盖）。已修：赋值时若源无键而目标有键则保留目标键（与 `overwritePreservingLinks` 同规则）。

**A17. 【新增】`std::get` 不可用于 `JsonEntry`** — 低（未改）
结构绑定能工作是因为 ADL 找到 `ZJSON::get`，但 `std::tuple_size/tuple_element` 虽已特化，`std::get<0>(entry)` 这种带 `std::` 的写法编译不过。建议补 `namespace std { get<I>(...) }` 转发或在文档中说明（R5 工程化项）。

**A18. 【新增】`operator[]` 返回副本导致"就地修改无效"** — 文档级
`doc["a"].add(...)`、`copy["items"].take(0)` 修改的是副本（有测试锁定该行为）。这是 P1/F2 的直接动机，文档必须显式说明"取值用 `[]`，改结构用 `take`+`add` 或（R3 后）引用访问族"。

### 2.2 性能问题（复核后保留，标注实测状态）

**P1. `operator[]` / `at()` / `find()` / `take()` 全部按值返回** — 成立（最大黑洞）
更正：**标量成员**的副本开销很小（`StoredString` 拷贝 + `double`），真正的代价在**容器成员**（整棵子树深拷贝）。链式 `j["a"]["b"]["c"]` 在每层都可能深拷贝。
方案不变：新增引用访问族（`atRef`/`findPtr`/`get_ref`），内部实现（`applyPatch`/`mergePatch`）切换为指针访问；旧接口保留。

**P2. 数值转换链路** — 大部分已在本轮落地
解析侧 `from_chars` 已替换；`appendNumber` 的整数快路径、`to_chars` 浮点快路径此前已在位；`estimateSerializedSize` 对 Number 估 32 B（偏保守，可降到 24 B——double 最短往返表示最长 24 字符）。

**P3. 节点体积（数字已更正）** — 结构性优化，收益最大
实测（clang 22 / libc++ / x64）：`sizeof(std::string)=24`、`sizeof(detail::StoredString)=64`、**`sizeof(Json)=176`**。
拆解：4 指针 32 + `Type` 4 (+4 padding) + `valueString` 64 + `double` 8 + `name` 64 = 176。
（MSVC x64 的 `std::string` 为 32 B，对应 `StoredString=72`、`Json≈192`。）
对比 RapidJSON 的 16 B 节点差距依旧巨大 → R2 仍是第一阶段最大单点收益。注意原报告"StoredString ~96B×2、合计 ~170B"的数字**不成立**；`name`/`valueString` 合并 + union 后的目标值需以实测为准（约 100~120 B 量级，而非 96 B）。

**P4. keymap 代价模型** — 成立
`unordered_map<string, Json*>` 每键一次 string 分配；任何 append 全量作废；`reserve(16)` 写死。
方案：`unordered_map<string_view, Json*>`（键视图指向节点自身的 `name`，生命周期由节点/arena 保证）；append 增量插入，仅 `remove`/改键才作废；按已知子节点数 `reserve`。
**注意**：`buildKeymap` 现已纳入空键；改为 `string_view` 键后，`removeDirectChildrenByKey` 等删除路径必须同步作废 keymap（现有纪律已保持，需继续在测试中断言）。

**P5. 生命周期粘滞（arena shared_ptr 钉住源文档）** — 成立
更正：`detach()` 的"短字符串内联"阈值不是 23 B，而是 **15 B**（MSVC/libstdc++ 的 SSO 容量；libc++ 为 22 B，实现取保守值 15）。
另需注意：`parse(const std::string&)` 目前**必然复制整份输入**（`StringArena` 用 `shared_ptr<string>` 拥有文本，实测：解析后改写源字符串不影响结果）。要做到零拷贝，必须让调用方保证输入生命周期（新增 `parse(std::string&&)` 移动重载 + 显式文档化的"借用视图"入口），不能把 `const string&` 入口偷偷改成借用——那会造成悬垂视图。

**P6. 散点 O(n) 叠乘** — 成立
`size()` 每次全链遍历（`take/takes/slice/removeLast` 内部反复调用 → O(n²)）；`equalsObject` O(n²)（**须保留重复键多重集语义**）；`FromFile` 逐字符 `istreambuf_iterator`；`dump`/`operator<<` 先建整串。
**补充**：`toString()` 还会额外走一遍 `estimateSerializedSize()` 全树预遍历（O(n) 二次遍历），可考虑改为增量写入或按 arena 源长度做上界提示。

**P7. 解析热路径微优化** — 成立
空白跳过可查表/字长跳；`parse_stored_string` 可用 `memchr('"')` 大步扫描；`parse_number` 分支顺序可调。
**Frame 尺寸更正**：原报告写"~280 B/层"。按代码算术：`Json*` 8 + `StoredString` 64 + `smallKeyIndex`（16×24=384）+ `size_t` 8 + `unordered_map`（MSVC 64 / libc++ 40）+ 状态位 ≈ **520~560 B/层**，其中 384 B 是 16 槽小索引。把阈值降到 4~8 或改为"链上原子比较"能显著降低 `stk` 扩容与搬家成本。

## 3. 与主流库对比定位（校正后）

| 维度 | zjson 现状 | nlohmann | RapidJSON | simdjson |
| --- | --- | --- | --- | --- |
| 解析速度 | 中（视图 + 池已及格） | 慢（DOM 抽象重） | 快 | 极快（SIMD/On-Demand） |
| 内存/节点 | **176 B（实测 libc++）** | variant 树，仍重 | 16 B | 极小（tape） |
| 保序 | ✅ 天然 | 需 `ordered_json` | ❌ | ✅ |
| int64 保真 | ❌ | ✅ | ✅ | ✅ |
| locale 安全 | ✅（本轮已修小数路径） | ✅ | ✅ | ✅ |
| SAX | ❌ | 部分 | ✅ | On-Demand |
| Pointer/Patch/MergePatch | ✅ 全 | Pointer/Patch | Pointer | 需手写 |
| 错误定位（行列） | ✅ | ❌ | ❌ | ✅ |
| 分配器可插拔 | ❌（内置**每线程** slab，永不释放、无锁） | `std::allocator` | ✅ | 内部 |
| 深树不爆栈 | 解析 ✅ / 自建树 ❌ | ❌ | ❌ | 不适用 |

结论不变：**对齐目标 = "RapidJSON 的内存布局 + nlohmann 的功能面"**，不追 SIMD 前端。
C++17 最佳实践落点（补充校正）：
- `std::variant`/union + `if constexpr` 做紧凑存储（不要继承/虚函数）。
- `string_view` + 自定义哈希做零拷贝键索引（键生命周期由节点保证）。
- 文档级 arena 用 `std::pmr::monotonic_buffer_resource` 是可以的，但**它的 `deallocate` 是 no-op**，与"单节点删除"语义冲突 → 保留 slab + freelist，另提供"整树释放"路径（R4）。
- `[[nodiscard]]`/`noexcept`/`inline constexpr`/结构化绑定全量规范化。
- **深树路径改为迭代**（析构、克隆、pretty 打印、estimate）：这是"不会崩"的硬要求（A14）。

### 5.4 仍然无法用单测覆盖、需靠工具的部分（必须在 CI 落地）

1. **真正的泄漏检测**：单测只能验证"分配次数收敛"。堆块级泄漏（例如节点块没还池）需要 ASan/LSAN。
   → 现状：Windows(clang64) 的 ASan 已本地跑通（12/12，Debug），可捕获越界/UAF；但该平台 **不含 LeakSanitizer**。
   → 行动：新增 `x64-asan` 预设（MSVC `/fsanitize=address`）+ Linux CI（`-fsanitize=address,undefined` 并启用 LSAN），把 `ctest` 全量跑在 ASan/LSAN 下；Windows 侧保留 clang64 ASan 作为日常回归。
2. **跨线程释放（已修复）**：`thread_local` slab 在"线程 A 分配、线程 B 释放"时会把 A 的块压进 B 的空闲链，A 线程退出时整片释放自己的 slab → 若 B 仍持有该块即为悬垂。上游 `24189fd` 已把池改为"进程生命期 + mutex + 永不析构"，本版复核用 ASan 做了合并前后对照（§8.3），并补了 3 个回归用例。
   → 残留：跨**模块卸载**（header 被内联进多个共享库，其中一个被卸载时其 slab 被回收）仍不安全；池的每线程驻留按其峰值保留（§8.6 已给出设计取舍与实测数据）。
3. **并发热点**：`keymap`/`strRef()` 的 mutable 写入需 TSAN 验证。

## 9. 第三方审核报告（2026-09-14）的复核结论

第三方对 `a3a3778..HEAD` 的 8 次提交做了独立审核（见 [`改造审核报告-2026-09-14.md`](改造审核报告-2026-09-14.md)）。本节记录**我方逐条复现的结果**：确认哪些为真、有无加重、已修哪些、剩下什么。复现程序（一次性，不入库）覆盖 F1/F2/F3/F5。

### 9.1 F1：赋值运算符丢失兄弟链 —— **确认，且比报告描述更严重（已修）**

`operator=`（拷贝与移动）都无条件把 `this->brother` 置空（移动分支改为取 `rhs.brother`）。成员节点是容器链上的一环，赋值等于把它摘链。实测：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `for (auto& [k,v] : doc) v = Json(5);`（3 成员，拷贝赋值） | `{"alpha":5}` | `{"alpha":5,"beta":5,"gamma":5}` |
| 同上（移动赋值） | `{"alpha":7}` | `{"alpha":7,"beta":7,"gamma":7}` |
| 只给中间成员赋值（`beta`） | `{"alpha":1,"beta":42}`（gamma 丢失） | `{"alpha":1,"beta":42,"gamma":3}` |
| 数组元素逐个赋值 `[1,2,3]` | `[0]` | `[0,0,0]` |
| 整文档赋值 `a = b`（本来的用途） | 正确 | 正确 |

报告称“只改到第一个成员”，实测**是“最后一个成员之外的都会丢”**：任何非尾成员的赋值都会丢掉它后面所有兄弟（对象/数组皆然）。三者后果齐备：数据丢失、静默无报错、脱链子树不可达（本库池永不释放，进程级无害但逻辑泄漏）。

**修复**：两个赋值运算符改为保存/恢复 `this->brother`（不再读 `rhs.brother`），与 `overwritePreservingLinks()` 同规则。见 `src/zjson.hpp` 的 `operator=`。

**测试**：报告指出 `tests/test_api_coverage.cpp` 的迭代器用例只改首个成员而掩盖缺陷——属实。已把该用例改为**整循环赋值**并断言全文档，另新增 `assignment_through_iterators_keeps_every_member`（拷贝/移动/中间成员/数组元素/替换为容器/复用不漂移/整文档赋值共 7 组）。

### 9.2 F2：三参 `remove(key, self, prev)` —— **确认，且严重性上调（已修）**

报告定位正确（容器归属固定为 `this`）。但实测后果**比“归属错误”更重**：链被拼接进无关节点后，文档被写成大量未初始化节点，随后 **SIGSEGV**。

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 历史递归形态 `doc.remove("k", &p 的首子, &p)` | 文档被写坏 + 段错误 | `{"p":{"x":2,"y":3},"tail":9}` |

**修复**：按历史约定从 `prev` 推导链属主（`container = prev ? prev : this`，初始前驱为 `nullptr`），并在注释里写明“`self` 必须是 `prev`（或 `this`）的首个子节点”。内部已无调用路径，改动只影响这个历史形态。**测试**：新增 `three_argument_remove_uses_the_owner_supplied_by_the_caller`（含事后 add/remove 仍可用 + 单参深层删除不变）。

### 9.3 F3：线程 churn 下的池驻留 —— **确认，已量化**

实测：**64 个短命线程**各自建 4 万节点文档后退出 → 进程**永久增长 440MB**（≈6.9MB/线程）。报告估算的每 slab ≈180KB（1024×176B）与量级一致。属设计取舍（换取无锁 + 跨线程安全），但“每请求一线程”的模型确实会无上界增长。→ 行动项见 §9.5 P1。

### 9.4 F4 / F5 / F6 —— 确认（低风险）

- **F4 确认**：`parseLeadingDoubleImpl` 的 `invalid_argument` 回落 `std::atof` 仍受 locale 影响；只有 inf/nan/hex 字符串命中该分支，正常数字走 `from_chars` 已安全。

### 8.6 mutex 开销与 LSAN 豁免（**已闭环**，2026-09-14）

#### (1) mutex 开销：实测不可接受，改为无锁的每线程池

用 `bench/`（`bench/bench_main.cpp` 新增 `zjson node pool cost` 诊断项：单线程 create+destroy 密集 churn + 1 线程 vs 4 线程 parse+stringify）实测，同机三次运行：

| 方案 | churn（每次 create+destroy） | 单线程 parse+stringify | 4 线程聚合 | 扩展比 |
| --- | ---: | ---: | ---: | ---: |
| 共享池 + `std::mutex`（`24189fd` 原方案） | 42.7 ~ 45.4 ns | 69.5 ~ 81.3 MB/s | 31.6 ~ 35.1 MB/s | **×0.42 ~ 0.47** |
| **每线程池 + 永不释放 + 无锁（本版采纳）** | **25.4 ~ 29.6 ns** | **90.6 ~ 95.4 MB/s** | **244.3 ~ 265.8 MB/s** | **×2.56 ~ 2.94** |

结论：共享 mutex 把 4 线程变成"比单线程还慢一倍"，单线程也多付 15%+，**判定为不可接受**。已按预定备选方案实施：

1. 池回到 `thread_local`，但**不恢复析构函数**（slab 永不释放）——这是跨线程释放安全的前提：无论块被压在哪个线程的空闲链上，它指向的内存永远有效；
2. 因为每个线程只碰自己的池，**完全去掉了锁**（这是 4 线程扩展比回到 ×2.6 的直接原因）；
3. 块大小改为**编译期常量**（`SlabAllocator<sizeof(Json)>`）：这样"是 slab 块还是超大块"的判定在**任何线程**都成立——包括"本线程从未分配过、却在释放别的线程分配的节点"这种场景（否则该线程 `blockSize == 0` 会把 slab 块误判为超大块而错误地走 `::operator delete`，这是 thread_local 化会引入的新坑）；
4. 保留 A1 修复（超大块回退 `::operator delete`，现在靠 `size != blockSize` 判定，与线程状态无关）。

代价与边界（写进 README 的线程契约）：每个线程的内存驻留按其**峰值**保留（不跨线程回收）；跨 **DLL 卸载**仍不安全（header 被内联到多个模块，某模块卸载时其 slab 被回收）；**同一棵树仍不支持并发读写**（A7 不变）。

#### (2) LSAN 豁免：已在代码与 CI 两处落地

| 位置 | 实现 |
| --- | --- |
| 头文件（对外生效） | `markPoolMemoryResident()` 在 `addSlab()` 里对每个 slab 调 `__lsan_ignore_object()`。仅在**检测到 ASan 且非 Windows**（LSAN 不存在于 Windows，无运行时会链接失败）时编译进来，其余情况为空操作 |
| 构建/CI（兼备） | `tests/lsan.supp` 提供 `leak:SlabAllocator` / `leak:jsonNodeAllocator` 抑制；CMake 在 `CMAKE_ZJSON_ENABLE_ASAN=ON` 时为**全部测试**注入 `LSAN_OPTIONS=suppressions=...`（已确认写入 `CTestTestfile.cmake`） |

验证现状：clang64 上 ASan 套件 12/12 通过（该平台无 LSAN，豁免路径编译为空操作）；非 Windows 分支用桩头文件做了**编译验证**（`extern "C" void __lsan_ignore_object(const void*)`），确认调用点类型正确；真正的"无泄漏上报"仍需 Linux CI（LSAN）实测，已列入 R5 工程化项。

### 8.7 这是"功能问题"还是"特定需求"？

两者都不是**功能**层面的问题，需要分开看：

- **流程层面**（为什么漏掉）：基线漂移——评审前没 pull。工程流程问题，与库的功能无关，预防措施见 8.1。
- **技术层面**（这个提交修什么）：属于**非功能性需求**（内存生命周期 + 线程模型），不是"某个用户提的特殊需求"：
  - 只在**单线程使用且对象不跨模块传递**时不受影响——从这个角度，多线程确实属于"特定使用场景"；
  - 但本库是 header-only、`Json` 是可移动的值语义类型，对象跨线程/跨模块传递是**常见用法**（工作线程解析 → 主线程消费是最典型模式），一旦发生就是**静默内存错误**，因此应按**通用正确性修复**处理，而不是可选需求。
- **结论**：把它当"特定需求"只在"我们承诺库仅单线程使用"的前提下才成立；当前文档没有这种承诺（A7 只说明树本身非线程安全），所以合并是正确选择。同时应在 README 明确线程模型契约：(1) 节点分配/释放线程安全；(2) 同一棵树不支持并发读写；(3) 跨 DLL 传递对象仍有残留风险。
